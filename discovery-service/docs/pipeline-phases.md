# Discovery Pipeline Phases

Internal developer documentation for the discovery pipeline phase architecture,
step sequencing, state tracking, and partial failure tolerance.

## Overview

The discovery pipeline transforms raw repository contents into structured
architecture candidates through a sequence of phases. Phase 0 establishes
configuration; Phase 1 (steps 1a through 1d) performs extraction, inference,
clustering, and candidate generation.

All Phase 1 steps are orchestrated by the `startRun` function in
`discovery-service/src/services/runManager.ts`.

## Phase 0: Configuration and Setup

Phase 0 is a precondition, not an executable pipeline step. It establishes
the discovery configuration that downstream steps consume:

- **Repository list**: URLs and branches to analyze
- **Include/exclude path filters**: glob patterns controlling which files
  are analyzed
- **Repo-to-application mappings**: Phase 0 anchor hints linking repository
  paths to known application names (used in Phase 1c and 1d for anchor
  assignment and candidate naming)

Configuration is persisted as a `DiscoveryConfigEntity` in the
architecture-model-service and loaded as a `config_snapshot` on the
discovery run record before Phase 1 begins.

## Phase 1a: Universal Extraction

**Purpose**: Extract language-agnostic evidence atoms from configured
repositories.

**Inputs**:
- `AnalyzerInput` with `context` containing the `config_snapshot` (repos,
  includePaths, excludePaths, runId)
- Repository source code (cloned via `RepoAccessProvider`)

**Execution**:
1. The `phase1aAnalyzerPack` (`discovery-service/src/services/phase1aAnalyzerPack.ts`)
   is invoked via the analyzer registry.
2. For each configured repository:
   a. Clone the repository to a temporary directory.
   b. Run three sub-extractors in parallel:
      - `fileStructureExtractor` -- produces `file_structure` atoms (path, extension, size, line count)
      - `symbolExtractor` -- produces `symbol` atoms (name, kind, line, scope, language)
      - `stringPatternExtractor` -- produces `string_pattern` atoms (patternName, matchedText, line, contextSnippet)
   c. Collect all atoms; clean up the cloned directory.
3. If a repository clone fails, the error is logged, the repo is marked as
   failed in metadata, and processing continues with remaining repos.

**Outputs**:
- `EvidenceAtom[]` -- array of evidence atoms, each with a deterministic
  `id` generated by `generateEvidenceId(runId, repoUrl, filePath, type, distinguishingKey)`
  (see `discovery-service/src/utils/evidenceId.ts`)

**Persistence**:
- Atoms are persisted via `archModelClient.bulkSaveEvidence` in batches of
  `BULK_SAVE_BATCH_SIZE` (500).

**Step result metadata** (stored in `stepsPayload['1a']`):
- `atomCounts`: breakdown by type (`file_structure`, `symbol`, `string_pattern`)
- `totalAtoms`: total count
- `reposProcessed` / `reposFailed`: repository processing summary

## Phase 1b: Relationship Inference

**Purpose**: Infer relationships (imports, calls, extends, contains,
uses_data, defines, references) between Phase 1a evidence atoms.

**Inputs**:
- All Phase 1a `EvidenceAtom[]` for the run (fetched from the
  architecture-model-service; paginated if count exceeds `PAGINATION_THRESHOLD` of 5000)

**Execution**:
1. Fetch all 1a atoms. If the atom count exceeds 5000, atoms are fetched in
   pages of `PAGINATION_PAGE_SIZE` (2000) using offset/limit query parameters.
2. Run all registered `LinkerRule` implementations against the in-memory atom
   set. Each rule receives the full atom array and returns
   `CandidateRelationship[]` with confidence scores. Rules operate on the
   in-memory set and do not re-fetch atoms (no N+1 pattern).
3. Triage all candidate relationships via the `triageCandidates` function
   (`discovery-service/src/services/triageEngine.ts`):
   - **Auto-accepted** (confidence >= `AUTO_ACCEPT_THRESHOLD` = 0.8):
     Converted to `EvidenceRelationship` records and persisted directly.
   - **Ambiguous** (confidence >= `AMBIGUOUS_THRESHOLD` = 0.4 and < 0.8):
     Routed to the DecisionTask engine. Competing groups (same sourceAtomId +
     relationshipType) become `resolve_competing_relationships` tasks; others
     become `confirm_relationship` tasks.
   - **Discarded** (confidence < 0.4): Dropped without persistence.
4. Dispatch pending DecisionTasks to the gateway for LLM resolution.
5. Apply LLM results: confirmed relationships are persisted; rejected ones
   are discarded.
6. Assign deterministic IDs via `generateRelationshipId(runId, sourceAtomId, targetAtomId, relationshipType)`.

**Outputs**:
- `EvidenceRelationship[]` -- persisted relationships with stable IDs

**Persistence**:
- Auto-accepted and LLM-confirmed relationships are persisted via
  `archModelClient.bulkSaveRelationships` in batches of `BULK_SAVE_BATCH_SIZE` (500).

## Phase 1c: Evidence Clustering

**Purpose**: Group related atoms and relationships into coherent clusters
representing architectural boundaries (service boundaries, data domains,
shared libraries, API layers, UI modules, package modules).

**Inputs**:
- All Phase 1a `EvidenceAtom[]` for the run (paginated if > 5000)
- All Phase 1b `EvidenceRelationship[]` for the run (paginated if > 5000)

**Execution**:
1. Fetch all atoms and relationships (with pagination if needed).
2. Run registered `ClusteringRule` implementations via the clustering engine
   (`executeClusteringPasses`). Rules operate in ordered passes, where later
   passes can see clusters from earlier passes. Each rule returns
   `CandidateCluster[]` with members, type, confidence, and formation reason.
3. Triage candidate clusters via the `triageClusterCandidates` function
   (`discovery-service/src/services/clusterTriageEngine.ts`):
   - **Auto-accepted** (confidence >= threshold): Persisted directly.
   - **Ambiguous**: Routed to DecisionTask engine for LLM resolution.
     Ambiguity types include:
     - `cluster_merge_decision`: Two clusters with significant overlap
     - `cluster_type_classification`: Cluster with unclear architectural type
     - `cluster_anchor_assignment`: Cluster needing Phase 0 anchor mapping
     - `cluster_noise_decision`: Cluster flagged as potential noise
   - **Discarded**: Dropped.
4. Dispatch DecisionTasks to gateway for LLM resolution.
5. Apply adjudication results (merge decisions, type corrections, anchor
   assignments, noise removal).
6. Perform delete-and-recreate persistence for the final cluster set.
7. Assign deterministic IDs via `generateClusterId(runId, clusterLabel, clusterType)`.

**Outputs**:
- `EvidenceCluster[]` -- each with `id`, `runId`, `clusterType`, optional
  `name`, `confidence`, `members` array (atom and relationship references),
  `data` metadata, `formedAt` timestamp

**Persistence**:
- Final clusters persisted via `archModelClient.bulkSaveClusters` in batches
  of `BULK_SAVE_BATCH_SIZE` (500).

## Phase 1d: Candidate Generation

**Purpose**: Synthesize discovery candidates (proposed meta-model elements)
from clusters, atoms, and relationships.

**Inputs**:
- All Phase 1c `EvidenceCluster[]` for the run
- All Phase 1a `EvidenceAtom[]` for the run
- All Phase 1b `EvidenceRelationship[]` for the run

**Execution**:
1. Fetch all clusters, atoms, and relationships.
2. Run registered `CandidateGenerationRule` implementations via the
   multi-pass candidate generation engine (`executeCandidateGenerationPasses`).
   Each rule receives clusters, atoms, relationships, existing proposals from
   prior passes, and config, and returns `CandidateProposal[]`.
3. Triage proposals via `triageCandidateProposals`
   (`discovery-service/src/services/candidateTriageEngine.ts`):
   - **Auto-accepted** (confidence >= `CANDIDATE_AUTO_ACCEPT_THRESHOLD` = 0.75):
     Persisted directly as `DiscoveryCandidate` records.
   - **Ambiguous** (confidence >= `CANDIDATE_AMBIGUOUS_THRESHOLD` = 0.35 and < 0.75):
     Routed to DecisionTask engine. Ambiguity types include:
     - `candidate_type_classification`: Unclear meta-model element type
     - `candidate_parent_assignment`: Ambiguous parent-child relationship
     - `candidate_name_refinement`: Weak or generic candidate name
     - `candidate_merge_decision`: Two candidates with 35-70% cluster overlap
     - `candidate_rejection_review`: Discarded candidate with salvageable signals
   - **Discarded** (confidence < 0.35): Dropped (but salvageable ones may
     generate `candidate_rejection_review` tasks).
4. Dispatch DecisionTasks to gateway for LLM resolution.
5. Apply adjudication results (type corrections, parent assignments, name
   refinements, merges, rejections/rescues).
6. Perform delete-and-recreate persistence for the final candidate set.
7. Assign deterministic IDs via `generateCandidateId(runId, candidateName, candidateType, parentCandidateId)`.

**Outputs**:
- `DiscoveryCandidate[]` -- each with `id`, `runId`, `candidateType`, `name`,
  `confidence`, `status`, `sourceClusterIds`, `data`, `synthesizedAt`,
  optional `parentCandidateId`, optional `logEnrichment`

**Persistence**:
- Final candidates persisted via `archModelClient.bulkSaveCandidates` in
  batches of `BULK_SAVE_BATCH_SIZE` (500).

## Step Sequencing in `startRun`

The `startRun` function (`discovery-service/src/services/runManager.ts`, line ~2040)
orchestrates step execution:

```
VALID_STEPS = ['1a', '1b', '1c', '1d']
```

For each step in order:

1. **Mark step as running**: Set `stepsPayload[step] = { status: 'running', stepStartedAt }`.
2. **Emit structured log**: `step_start` event with `runId`, `projectId`, `step`, `timestamp`.
3. **Validate state transition**: Call `validateStatusTransition(currentRunStatus, 'RUNNING')`.
   Valid transitions are defined in `VALID_TRANSITIONS`:
   - `PENDING -> RUNNING`
   - `RUNNING -> RUNNING` (for subsequent steps)
   - `RUNNING -> COMPLETED`
   - `RUNNING -> FAILED`
4. **Update run record**: Persist status `RUNNING` with `current_step` and `steps_payload`.
5. **Execute step**: Call `executeStep(step, projectId, runId)` which dispatches to
   `executeStep1a`, `executeStep1b`, `executeStep1c`, or `executeStep1d`.
6. **Mark step as completed**: Set `stepsPayload[step]` to include `status: 'completed'`,
   all step result metadata fields, `stepStartedAt`, `stepCompletedAt`, `durationMs`.
7. **Emit structured log**: `step_complete` event with timing and count data.
8. **On final step**: Validate transition to `COMPLETED`, update run record,
   emit `run_complete` event with total `durationMs`.

## stepsPayload State Tracking

The `stepsPayload` is a `Record<string, Record<string, unknown>>` initialized
with all steps set to `{ status: 'pending' }` and accumulated across the
step loop.

Each step entry progresses through these states:

| State | Fields |
|---|---|
| `pending` | `{ status: 'pending' }` |
| `running` | `{ status: 'running', stepStartedAt }` |
| `completed` | `{ status: 'completed', ...stepResult, stepStartedAt, stepCompletedAt, durationMs }` |
| `failed` | `{ status: 'failed', errorMessage, step }` |

The `stepsPayload` is persisted to the run record after every state change,
ensuring that on failure, all previously completed steps retain their full
metadata.

## Partial Failure Tolerance

When a step throws an exception:

1. The failing step's `stepsPayload` entry is set to
   `{ status: 'failed', errorMessage, step }`.
2. All prior completed steps retain their full `stepsPayload` entries
   (including timing, counts, and metadata) because the `stepsPayload`
   object is accumulated across the loop, not reset.
3. The `error_message` field on the run record includes the step identifier:
   `Step ${step} failed: ${errorMessage}` (e.g., "Step 1c failed: connection timeout").
4. The run status transitions to `FAILED`. If the current state allows the
   `FAILED` transition, the update is validated; otherwise, the update is
   attempted without validation to ensure the error is persisted for
   diagnostics.
5. A structured log event `run_failed` is emitted with total `durationMs`,
   error message, and stack trace.
6. The function returns immediately (fail-fast, no retry).

After a failed run, a fresh `POST /discovery/runs` creates a new independent
run that re-executes from step 1a without interference from the failed run's
data. Each run has its own UUID, and evidence/relationship/cluster/candidate
records are scoped to that run via `runId`.
