# Kratos framework guidance

A `kratos` static analysis pack has already been run against this file.
Its output is injected into the prompt as a fenced JSON array. You are
here to surface what that pack CANNOT see — not to restate what it
already captured.

Kratos is Bilibili's Go microservice framework (`github.com/go-kratos/
kratos`). It is opinionated: protobuf-driven service contracts, Wire
for dependency injection, a four-layer architecture (`api` / `biz` /
`data` / `service` + `server` plumbing), and a middleware chain
wrapping every transport. The deterministic pack covers a narrow slice
of this — the structural surface only — and leaves the framework's
real architectural spine (the .proto contracts, the Wire graph, the
middleware ordering) entirely to this LLM layer.

## What the adapter already catches (do NOT re-emit these)

- **gorm-tagged structs** — any Go struct where at least one field
  carries a backtick tag starting with `gorm:`. Emitted as a
  `physical_data_entities` candidate with a naive pluralised table name
  (`User` → `users`).
- **gorm-tagged struct fields** — each field of a gorm-tagged struct.
  Emitted as `physical_data_attributes` candidates with the column name
  extracted from `gorm:"column:<name>"` when present, and
  `isPrimaryKey=true` when the tag contains `primaryKey`.
- **json-only DTO structs** — Go structs where fields have `json:`
  tags but NO `gorm:` tags. Emitted as `logical_data_entities` candidates
  (request / reply shapes).
- **json-only DTO struct fields** — each field of a json-only struct,
  emitted as a `logical_data_attributes` candidate.
- **gRPC service-interface types** — Go interface types whose name
  ends in `Server`, `Service`, or `Client`. Emitted as `interfaces`
  candidates with `controllerType: 'KratosService'`. These are the
  interface types generated by `protoc-gen-go-grpc` /
  `protoc-gen-go-http` from `.proto` definitions, plus hand-written
  interfaces that follow the naming convention.

Anything in that list is presumed ALREADY PRESENT in the pack output.
Emitting duplicates of those is the primary failure mode for this
layer.

## What the adapter MISSES (your target surface area)

Surface candidates the pack does not see. Typical Kratos / Go-
microservice blind spots:

- **Protobuf service contracts.** The pack detects Go interface types
  with `Server` / `Client` suffixes generated from .proto files. It
  does NOT parse the underlying `.proto` IDL, so the **individual RPC
  methods** (`rpc GetUser (GetUserReq) returns (GetUserReply)`), the
  **message definitions** (`message User { ... }` with protobuf field
  types, enums, nested messages, oneofs), the **HTTP binding
  annotations** (`option (google.api.http) = { get: "/v1/users/{id}"
  };`), and the **service-level options** (deadlines, auth rules)
  are invisible. For each `.proto` file (under `api/` or `proto/`),
  emit the service + every RPC as an `endpoints` candidate with its
  HTTP verb + path from the `(google.api.http)` annotation, and emit
  the message definitions as `logical_data_entities` + `logical_data_attributes`
  candidates distinct from whatever the `.pb.go` struct inheritance
  captured.
- **Wire dependency-injection wiring.** Kratos uses Google Wire for
  DI. `wire.go` files declare `wire.Build(...)` with a slice of
  provider-set references; `wire_gen.go` is the generated injector.
  The **`wire.NewSet(...)` provider sets** (typically named
  `ProviderSet` in each package — `biz.ProviderSet`, `data.ProviderSet`,
  `service.ProviderSet`) declare which constructors participate in
  the graph. Each `wire.Bind(new(Interface), new(*Concrete))` binds
  an interface to its concrete implementation — this is where the
  `UserRepo` interface is wired to `*userRepo`. Emit the Wire graph
  as cross-cutting architecture candidates: each provider set as a
  module, each binding as a (concrete → interface) dependency.
  Provider dependency cycles (if any) are latent bugs — flag them.
- **Middleware chain order.** `server/grpc.go` and `server/http.go`
  construct the transport via `grpc.NewServer(grpc.Middleware(...))`
  or `http.NewServer(http.Middleware(...))`. The middleware slice
  inside — typically `recovery.Recovery()`, `tracing.Server(...)`,
  `logging.Server(logger)`, `jwt.Server(...)`, `ratelimit.Server()`
  — runs in-order for every inbound request. The **ordering** is
  architecturally meaningful (recovery wraps everything, tracing
  before logging so spans contain the request id, auth after
  tracing, etc.). Emit each middleware as its own cross-cutting
  concern candidate, and surface the ordering as metadata — the pack
  only sees interface types, not these functional wrappers.
- **Metrics, tracing, and logging hooks.** Kratos integrates with
  OpenTelemetry (`go.opentelemetry.io/otel/sdk/trace`), Prometheus
  (`metrics.Server(...)`), and the framework's own `log.Helper`. The
  **TracerProvider initialization** (typically in `main.go` or
  `cmd/server/main.go`), the **metrics endpoint registration** (on
  the HTTP server or a sidecar endpoint), and the **log.NewHelper
  wrapping** at each layer are integration-point candidates the
  adapter misses entirely.
- **gRPC stream handlers.** Streaming RPCs (`rpc Watch (WatchReq)
  returns (stream WatchResp)` — server-side stream, client-side
  stream, or bidirectional) have a different method signature shape
  than unary RPCs (`func (s *Srv) Watch(req *WatchReq, stream
  Service_WatchServer) error`). The generated interface method
  signature contains `stream` type parameters. Stream handlers are
  long-lived connections, not request/response — flag them
  distinctly from unary endpoints because the observability,
  timeouts, and back-pressure characteristics differ.
- **Event publishers and subscribers.** Kratos does not prescribe a
  single message-bus library; common choices are Kafka
  (`segmentio/kafka-go`, `confluentinc/confluent-kafka-go`), NATS,
  RabbitMQ (`streadway/amqp`), Pulsar, or Redis Streams. Look for
  constructor patterns like `kafka.NewReader(...)`,
  `kafka.NewWriter(...)`, `nats.Connect(...)`,
  `amqp.Dial(...)` / `ch.Publish(...)` / `ch.Consume(...)`. Each
  publisher is an outbound integration; each subscriber / consumer
  is an inbound event-driven endpoint. The adapter sees none of
  these — the connection setup happens in `data/data.go` or
  `server/server.go` and never shows up as a struct tag.
- **Repository pattern layering.** The `biz` package declares
  interfaces (`type UserRepo interface { ... }`), the `data` package
  declares the concrete implementation (`type userRepo struct {
  data *Data; log *log.Helper }`) plus a `NewUserRepo(...) biz.UserRepo`
  constructor, and a blank assignment (`var _ biz.UserRepo =
  (*userRepo)(nil)`) pins the interface satisfaction at compile time.
  The adapter catches the interface (if its name ends `Server` /
  `Service` / `Client` — which `Repo` does NOT) only by accident.
  Surface each `*Repo` / `*Repository` interface as a repository
  contract, each `NewXRepo` constructor as a DI entry point, and
  each blank-assignment line as an interface-satisfaction assertion.
- **UseCase / Service layer orchestration.** The `biz` layer
  typically declares `UseCase` structs (`type UserUseCase struct {
  repo UserRepo; log *log.Helper }`) with methods that compose
  repository calls into domain operations. The `service` layer
  (handlers) delegates to these UseCases. Surface each UseCase as a
  domain service candidate — the deterministic adapter misses them
  because they carry no struct tags.
- **Cache integrations.** Redis / Memcached / in-memory caches wired
  through `data/data.go` (`rdb := redis.NewClient(&redis.Options{
  Addr: c.Redis.Addr })`) are cross-cutting infrastructure. Look for
  cache-key builders (`userCacheKey := func(...) string { return
  "user_cache_key_" + ... }`) and cache-get / cache-set wrapping
  around repository methods (`getUserFromCache` /
  `serUserCache`). Emit each cache binding as an integration point.
- **Auth / JWT integrations.** `middleware/auth/jwt.Server(...)` in
  the middleware chain, `jwt2 "github.com/golang-jwt/jwt/v4"` import,
  signing-key extraction — the auth contract is scattered across
  middleware setup (`server/grpc.go`) and JWT-payload parsing
  (`internal/pkg/auth/`). The adapter does not identify any of it.
- **Configuration binding.** `conf/conf.proto` → `conf/conf.pb.go`
  generates a `Bootstrap` / `Config` struct. `main.go` reads the
  YAML (`configs/config.yaml`) via `config.New(...)` and binds it
  into the generated proto struct, then the constructors pull
  sub-sections (`*conf.Server`, `*conf.Data`, `*conf.Auth`) into the
  Wire graph. Surface the config-bound structs as configuration
  surface — the connection strings, timeouts, and auth keys they
  carry are deployment contract.
- **`ent` ORM schema.** If `internal/data/ent/` exists, the service
  uses Facebook's `ent` ORM (not gorm). Schemas are declared as
  `ent.Schema` structs in `ent/schema/*.go` with `Fields()`,
  `Edges()`, `Indexes()`, `Annotations()` methods. `ent generate`
  produces the query / create / update fluent API in `ent/`. The
  adapter does NOT detect ent schemas — surface each ent schema as
  a `physical_data_entities` candidate, each `.Edge(...)` call as a
  `logical_data_entity_relationships` candidate, and note that ent uses
  code-generation, not struct tags.
- **Error registry.** Kratos codebases often declare an `api/.../
  *_error.pb.go` file per service (generated from
  `<service>_error.proto`) enumerating domain error codes. Each
  `ErrorReason_*` constant is a business-facing error surface.
- **HTTP binding / gateway routes.** For services that expose HTTP
  (`option (google.api.http) = { ... }` on RPC methods), `protoc-
  gen-go-http` generates `<service>_http.pb.go` with a
  `RegisterXHTTPServer(s *http.Server, srv XHTTPServer)` call. Each
  HTTP verb + path pair is an endpoint. The adapter sees the
  `XHTTPServer` interface; emit each individual HTTP route as a
  distinct `endpoints` candidate.

## Gap-fill targets (11th candidate type)

- **`interface_logical_entities`.** This framework's pack does NOT yet emit `interface_logical_entities` candidates. When an `interfaces` candidate (API controller, resolver, handler class) in this file references a `logical_data_entities` candidate (DTO, request/response body type) that is also defined somewhere in the project, emit an `interface_logical_entities` candidate named `InterfaceClass → LogicalDataEntityClass` (ASCII arrow, single spaces). Per-interface granularity — one entry per (interface, logical_data_entity) pair regardless of how many endpoints reference the DTO.
