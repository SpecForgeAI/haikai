# TypeScript language guidance

## Idioms to recognize

- **Decorators** on classes and methods are direct role markers when a
  framework is in use:
  - NestJS / backend: `@Injectable`, `@Controller`, `@Module`,
    `@Service`, `@Get`, `@Post`, `@Put`, `@Delete`, `@Patch`,
    `@EventPattern`, `@MessagePattern`, `@UseGuards`,
    `@UseInterceptors`.
  - Angular: `@Component`, `@Directive`, `@Pipe`, `@NgModule`,
    `@Injectable({ providedIn })`, `@Input`, `@Output`,
    `@HostListener`, `@ViewChild`.
  - ORM / validation: `@Entity`, `@Column`,
    `@PrimaryGeneratedColumn`, `@ManyToOne`, `@OneToMany`,
    `@IsString`, `@IsEmail`, `@MinLength`, `@ValidateNested`.
  - GraphQL / TypeGraphQL: `@Resolver`, `@Query`, `@Mutation`,
    `@Subscription`, `@ObjectType`, `@InputType`, `@Field`,
    `@Args`, `@Context`.
- **React component shapes.** PascalCase function / arrow-function /
  class exports that return JSX (or live inside `.tsx`) are the
  component surface. The naming convention is load-bearing — a
  PascalCase function that does not return JSX is NOT a component.
  Hooks are `use*` exports (camelCase). Do not conflate the two.
- **Type-only exports** (`export type`, `export interfaces`) often
  declare public contracts / DTOs that live at the boundary of a
  module. Treat interfaces named after business nouns as domain or
  DTO candidates; treat interfaces named after operations (`*Service`,
  `*Client`, `*Repository`) as service contracts.
- **Re-exports and barrel files** (`export * from './...'`,
  `export { X } from './X'`) collapse a module's public surface.
  Candidates usually live in the re-exported file, not the barrel
  file itself; prefer the implementation file path when emitting.
- **Arrow-function modules.** Plain `.ts` modules that export a set of
  related functions (`export const fooService = { ... }`, or
  `export async function doThing() { ... }`) are idiomatic services
  in Node/TS codebases. Name the candidate after the object or after
  the module, whichever is more meaningful.

## Extraction nuances

- **JSDoc business hints.** `/** ... */` blocks immediately above
  exports often carry a one-sentence business description. Lift that
  into the `description` field when concise.
- **Module boundary cues.** A folder whose `index.ts` exports a single
  named thing is typically one logical unit - name candidates after
  that thing, not after the file.
- **`type` vs `interfaces`.** A type alias of a string literal union
  (`type Status = 'open' | 'closed'`) is a domain enum, worth
  surfacing. A structural type alias for a config object is usually
  not worth emitting.
- **`.d.ts` files** are type declarations only - skip them entirely.
- **Test fixtures.** Files under `__tests__/`, ending in `.test.ts` /
  `.spec.ts`, or importing `jest` / `vitest` / `supertest` are test
  scaffolding - skip.
- **Generated clients.** Files with banners like
  `// This file is generated by openapi-generator` or
  `// DO NOT EDIT` should be ignored.
- **Decorator metadata**. Arguments to framework decorators carry
  real architectural metadata. `@Controller('articles')` names the
  path; `@Component({ selector, templateUrl })` names the HTML
  template; `@Entity('table_name')` names the backing table;
  `@Module({ imports, providers, exports })` names the DI graph.
  Lift those arguments onto the candidate's `data`.

## Confidence calibration for TypeScript

- Class with NestJS / Angular / TypeGraphQL / tsyringe decorator
  explicitly naming its role: 0.9+.
- React component whose name matches a page / screen / view
  suffix AND lives under `src/pages/` or a `routes/` config: 0.85+.
- Module-level function export with a business-named suffix
  (`createOrderService`, `patientRepository`): 0.75-0.85.
- Inference from imports alone (e.g. `@nestjs/microservices` import
  in an otherwise plain file): 0.6-0.75.
