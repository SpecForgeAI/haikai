Topic: Oracle coverage scoring — a single shared rubric that BOTH drives LLM scenario generation AND scores baseline completeness (api-migration-validation-service capture layer; + one AMS field to persist the coverage summary; + frontend surfacing), INCLUDING project-wide auth-negative coverage.

Problem: The capture service now generates thorough per-endpoint scenarios (Phase 1: happy_path / not_found / one-per-enum-value / filter-combo / bad_request via defaultScenarioSet) and keeps only the canonical capture per intended outcome (Phase 2: selectCanonicalCapture + reject-and-hide fumbles), but NOTHING MEASURES how much of each endpoint's behaviour the baseline actually pins. A "green" reconcile is only trustworthy if you know the oracle is thorough. Today there is no coverage score, no per-dimension achieved/missed visibility, and no project-wide auth-negative coverage.

Decisions ALREADY made (fixed constraints, do not relitigate):
1. ONE rubric, SHARED both ways: the SAME logic that SCORES completeness MUST be the logic that FORMULATES the LLM-driven requests. The generated scenario set IS the rubric (already true via defaultScenarioSet); the scorer scores those very same dimensions. NO divergence between generation and scoring (single source of truth).
2. Coverage score = per-endpoint AND overall = (rubric dimensions that achieved a canonical capture matching their intended outcome) / (total rubric dimensions). Computed from Phase-2's per-scenario canonical/errored outcomes (runManager scenarioCaptures + selectCanonicalCapture). Each MISSED dimension carries an honest human-readable reason.
3. Surface the coverage score at Save-as-Baseline AND on the readiness screen; warn when an endpoint's coverage is thin.
4. Project-wide auth negatives: a SMALL number of SESSION-level (not per-endpoint) auth-negative scenarios — no-token -> 401, bad-token -> 401/403 — run once against one representative endpoint. NO multi-role tokens. Requires a new auth-override path in the HTTP executor/tool (execute_http_request) so a scenario can send without/with-bad auth despite the session auto-injecting valid auth. Auth coverage = a project-level rubric dimension.
5. Persist the coverage summary on the capture session/baseline via ONE new AMS field, plain TEXT/JSON (avoid fragile DDL); next free Liquibase changeset is 189 (highest existing 188). Design the field so a later spec (baseline integrity & provenance) can read the coverage score and stamp it onto the immutable baseline.

This is Spec A of a 3-spec series (A=coverage scoring, B=full-response reconcile fidelity / break types, C=baseline integrity & provenance).
