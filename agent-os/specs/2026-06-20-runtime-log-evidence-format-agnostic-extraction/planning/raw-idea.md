TITLE: Runtime log evidence — format-agnostic extraction wired into migration readiness.

PROBLEM (diagnosed this session, verified in code):
The "Create Migration Delivery Plan" wizard shows "Insufficient runtime evidence" even when the user uploaded a large (27MB) full-day runtime log rich with API endpoints. Two independent breaks:
1. PARSER: the runtime-evidence extractor regex (discovery-service `src/services/runtimeEvidence/runDiscoveryRuntimeEvidence.ts` ~lines 93-94, HTTP_METHOD_PATH_REGEX = /\b(GET|POST|...)\s+(\/[^\s...]+).../) requires a path that starts with "/" IMMEDIATELY after the method. The user's real log is a bespoke SampleSvc trace where each request is `<reqId> > METHOD http://host:port/path` (an ABSOLUTE URL), plus `<reqId> > header: value` lines, a blank `<reqId> >`, then the JSON body, interleaved with log4j lines whose logger is bracketed (`[thread] [logger]`). The regex can't match `POST http://...` (absolute URL, not `/path`), so it extracts ZERO observations. Format detection also lands on unknown→plaintext, and the bracketed-logger lines fail the framework parser.
2. DEAD EVIDENCE BRANCH: uploading a runtime log only writes the file to disk + records metadata in `config_snapshot.inputArtifacts.logFiles[]` (gateway `discoveryRunLogService.ts` writeLogFilesAndPatchRun; AMS `DiscoveryRunService.java` patchLogFileArtifacts). The scan-time runtime stage (`runtimeEvidencePersistence.ts`) NEVER writes a `discovery_evidence` row — it only writes steps_payload + in-memory enrichment + (potentially) runtime_usage findings. The ONLY code that writes `source='log'` evidence is the Increment-14 logExtractors (`src/services/logExtractors/` endpointUsageExtractor.ts/serviceInteractionExtractor.ts/index.ts runAllLogExtractors), reachable ONLY from the stranded manual route `routes/logEnrichment.ts` (POST /discovery/log-enrichment) — never called by the scan/upload.
CONSUMER (the gap): AMS `service/migration/MigrationDiscoveryContextService.java` buildRuntimeUsageSummary (~lines 944-960): hasRuntimeEvidence = (runtimeEvidenceCount > 0 || runtimeFindingCount > 0); runtimeEvidenceCount = count of in-scope `discovery_evidence` rows with source=='log'; runtimeFindingCount = count of in-scope findings whose category ∈ {runtime_usage, runtime_log, log}. The `insufficient_runtime_evidence` gap fires when hasRuntimeEvidence is false. Scope = latest 3 COMPLETED runs of the CURRENT architecture. So both counts are structurally 0 today.

GOAL: extract HTTP request observations (and response/headers/body where the log contains them) from runtime logs of ARBITRARY format, robustly and cheaply, and PERSIST them so they count — clearing the gap and recording real runtime usage. "Deterministically parse every log format in the world" is unachievable, so use an LLM to RECOGNISE the format once on a small sample, then deterministic code to APPLY it to the whole file.

SETTLED SOLUTION (decisions already made by the user — carry as FIXED; do NOT relitigate):

QUALITY-FIRST ORDERING (deliberate inversion of cost-first): try to do the BEST extraction first; fall back to a flexible deterministic matcher only if the smart path fails.

0. INGEST precondition: the runtime log uploaded to a discovery run MUST actually be consumed by the runtime stage (today it is stranded on disk + config_snapshot metadata only). Wiring this in is part of the build.
1. PRE-SCAN + SAMPLE (cheap, streaming, no LLM): scan the WHOLE file for candidate request lines (an HTTP verb, OR `http(s)://`, OR a `/seg/seg` path token). Build 8-12 sample BLOCKS, each = a hit line plus ~10 lines BEFORE and ~30 lines AFTER (~40 lines, enough to span a full request→response cycle). Spread blocks across the file by BYTE OFFSET (not just the head — "first 150 lines" is explicitly too basic; the top is often startup banners). Dedup near-identical blocks (don't waste budget on one endpoint hammered all day). Truncate over-long individual lines (e.g. long token values). REDACT every block (reuse the existing redactor) before it leaves the process. Cap the total sample to a small token/char budget. If the pre-scan finds NO hits, fall back to offset-stratified head/middle/tail windows so the LLM still gets representative data.
2. KNOWN-FORMAT FAST PATH (richness-gated): try the existing structured parsers (CLF/combined/JSON-lines). Use deterministic structured extraction for the whole file ONLY IF it yields the RICH field set the log supports (method, path, request headers, request body, response status + body). If it comes back THIN (e.g. only method+path when the log clearly has more), do NOT settle — go to the LLM step. (Honest caveat: a plain CLF log has no bodies/responses to extract, so it fails the richness gate and falls to the LLM, which also cannot invent what isn't logged — we just take the best available; no harm, one extra call.)
3. LLM PATTERN INDUCTION: send the redacted sample blocks to the LLM; it returns a STRUCTURED RECIPE (record delimiter + field rules for all 5 fields: method, path, headers, body, response) OR "no pattern". VALIDATE the returned recipe by applying it to a HELD-OUT block the LLM did not see; if the yield is weak, re-sample with different/more blocks (BOUNDED retries) before giving up.
4. DETERMINISTIC FULL-FILE EXTRACTION: (a) if a validated recipe exists → a deterministic engine applies it across the FULL file (e.g. 27MB), pulling EVERY field the log actually contains (method, path, headers, body, response IF logged — never invent a response that isn't there); (b) if the LLM found no pattern OR its recipe failed validation → fall back to the single FLEXIBLE deterministic matcher (broadened to accept `METHOD <absolute-URL>` as well as `METHOD /path`, extracting method+path), which always at least clears the gap. CRITICAL invariant: the LLM ONLY ever sees the small redacted samples; the whole file is ALWAYS processed by deterministic code. PERSIST the inferred recipe on the run for free reuse on re-runs / same-source files (auditable).
5. PERSIST + WIRE (the dead-branch fix): turn extracted observations into COUNTABLE evidence — write `source='log'` discovery_evidence rows AND `runtime_usage` findings (matched to discovered endpoint candidates where possible). REUSE the existing Increment-14 logExtractors / evidence-writing path where possible (it already writes source='log' evidence) rather than net-new. This flips hasRuntimeEvidence true → the `insufficient_runtime_evidence` gap clears in the Migration Delivery Plan. The richer request bodies (real IDs, real date formats e.g. businessDate "09-Jun-2026", hierarchyId 2506859) become available as capture SEED DATA — adjacent benefit; confirm in shaping whether harvesting them is in THIS spec or a fast-follow.
6. SURFACE: runtime usage counts visible; gap cleared; recipe auditable.

OTHER FIXED CONSTRAINTS:
- LLM = a Claude model (latest/most capable default). One small call per file/format; recipe cached/persisted for reuse. Cost is bounded and must stay so.
- Optional cheap pre-check to short-circuit already-known standard formats straight to deterministic extraction is ACCEPTABLE only under the same richness gate (step 2).
- Redaction of samples sent to the LLM is mandatory.
- The user will NOT run another scan until this solution is built and good.
