TITLE: SOAP/WSDL message-field depth (Spec 4 of the HAIKAI discovery-richness program)

CONTEXT: HAIKAI is a like-for-like API/DB migration tool. A discovery scan + architect/PM conversations must be rich enough to be the migration specification ORACLE. This is the SOAP analogue of Spec 1 (which built the REST endpoint→data-effect graph). Program status: Issue 1 + Specs 1-3 + Issue 2 are built; Spec 4 + Spec 5 remain.

PROBLEM/GOAL: For a Java/Spring-Classic SOAP service, discovery currently stops at the OPERATION level and mints NO data entities — so the actual request/response MESSAGE-FIELD shapes crossing the SOAP boundary are invisible to the oracle. Spec 4 captures the full SOAP message-field structure (fields, types, cardinality, nullability, and validation restrictions) richly enough to (a) seed complete operation capture for the runtime equivalence harness and (b) be the DTO-shape oracle for migration.

CURRENT STATE (factual): SOAP detection works via 3 signals — Spring-WS annotations, JAX-WS annotations, and WSDL parsing (`discovery-service/src/services/findings/packFindingScanners/springClassicSoap/`). It emits `interfaces` (SOAP_API) + `endpoints` candidates with operation-level detail (operation name, soap_action, request/response root element + namespace, request/response DTO class NAMES). The WSDL/XSD parser (`wsdlParser.ts`) collects only top-level element/complexType NAMES — no field-level depth. THE GAP: no `logical_data_entities`/`logical_data_attributes` are minted from SOAP message schemas; no cardinality/nullability/restriction detail; no endpoint→message-entity binding.

META-MODEL GROUNDING (must conform to `gateway/src/config/prompts/shared/architecture-context-explainer.md`): SOAP message types → `logical_data_entities` (the reference defines these as API DTO shapes); message fields → `logical_data_attributes`; interface exposes types → `interface_logical_entities`; bind via the existing EndpointEntity.request_data_entity_point_id / response_data_entity_point_id. ARCHITECTURE (the meta-model) stays separate from REALITY (validation restrictions may be Findings, mirroring Spec 3). Never create the auto-managed `*_points` wrappers; never synthesize a 1:1 mapping.

CONSTRAINTS: AMS snake_case (no @CamelCaseWire); NEW Liquibase changeset files only (next >=167); no discovery-service/src edits during an in-flight run; LLM via the gateway relay. Reuse Issue 2's model-aware dedup + the save-back identity primitive.
