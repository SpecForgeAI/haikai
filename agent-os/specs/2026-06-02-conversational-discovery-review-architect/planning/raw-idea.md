**Spec 3 — Conversational discovery-review "Architect" persona (the capstone).**

The FINAL spec of a sequenced 5-spec discovery-review-unification program (F → 0 → 1 → 2 → 3). ALL deterministic groundwork is BUILT + verified:
- **Spec F**: findings normalized to the Approve/Reject/Defer vocabulary (shared with candidates).
- **Spec 0**: universal identity-keyed cross-source candidate MERGE + the conflict/provenance data model in candidate `data` (`_conflicts`/`_conflictResolutions`/`_addedBy`/`_mergedFrom`/`_attributeProvenance`), PLUS the defined "similarity class" for bulk conflict resolution (same attribute + same competing source-set) — the data model that makes bulk-resolve-by-pattern computable.
- **Spec 1**: the DETERMINISTIC review-model + typed cascade/dependency graph + surface-only blast-radius + aggregations backbone (discovery-service `reviewModel/`, the `GET /:runId/review-model` endpoint, gateway proxy, ≤1 code + ≤1 DB scan selection).
- **Spec 2**: cascade-aware ATOMIC bulk Approve/Reject/Defer/Save (the `@Transactional` AMS `bulk-review-cascade` endpoint), the pure `resolveBulkActionSet` helper (gateway-canonical `gateway/src/services/discovery/resolveBulkActionSet.ts`, DELIBERATELY built headless so THIS spec's coordinator can call it), and the real reject→downstream-IR suppression.

**Problem.** Today a user reviews discovery output through the candidate/findings GRID — a power-user surface that works without any LLM. But the program's North Star is to make review LESS daunting and MORE complete (oracle standard): a user faced with hundreds of merged candidates + findings across a code scan and a DB scan needs a guide. Spec 3 adds a conversational "Architect" persona that walks the user through the review in a chunked, narrated agenda, proposes dispositions with their cascade/conflict consequences, and applies confirmed decisions — all through the EXACT deterministic mechanisms Specs 0-2 already built.

**This spec adds the conversational layer (the ONLY spec that uses the LLM):**
1. **A hybrid "LLM proposes, orchestrator writes" persona.** DETERMINISTIC code owns ALL counts, cascades, conflicts, and actions (Specs 0-2). The LLM (GPT 5.x) does ONLY two things: (a) NARRATE facts it is handed (the chunk summary, the blast-radius, the conflict set) in plain language, and (b) MAP the user's natural-language intent into CONFIRMED, deterministic tool calls. The LLM never computes a count, never decides a cascade, never mutates state directly.
2. **A bounded tool/function surface** wrapping the deterministic backbone (every mutating call is confirmed before it fires): scan selection (≤1 code + ≤1 DB run, opening the conversation with "which code and/or DB scans are we reviewing?"); `getReviewChunk` (the chunked agenda — NEVER the firehose); `preview` (calls `resolveBulkActionSet` → the touched set + cascade provenance + net counts); `applyDecision` (the Spec 2 atomic `bulk-review-cascade` endpoint for Approve/Reject/Defer); `resolveConflict` + **bulk-resolve-by-pattern** (Spec 0's conflict model + the similarity class — the "you chose the JAX-RS source; there are 45 similar conflicts, resolve all the same?" flow, deferred from Spec 0 to HERE); and `save` (the Spec 2 bulk Save / `save-approved` path).
3. **A chunked review agenda.** The conversation segments the review into manageable chunks (never dumps the whole set) and walks them in a sensible order, narrating each chunk's facts and proposing dispositions, with the user confirming/adjusting via natural language OR the deterministic click-to-answer fallback.

**Hard constraints / locked cross-cutting decisions (from the program):**
- The conversation AUGMENTS the existing grid: SHARED decision store, the SAME approve/reject/save mechanisms (the Spec 2 endpoint + Spec 0 conflict resolution). The conversation is the RECOMMENDED entry; the GRID remains the power-user view AND the no-LLM fallback. They stay in sync (both read the Spec 1 model; both write via the Spec 2 atomic endpoint).
- REUSE the target-state "Architect Conversation" CHASSIS rather than building fresh: the persona pattern, the `RightHandPanelShell` RHS panel "room", the transcript-turn model, the decision-capture orchestrator ("LLM proposes, orchestrator writes"), and the DETERMINISTIC click-to-answer capture route (the no-LLM path) — all already exist for target-state (`frontend/src/components/targetState/architectConversation/` + `gateway/src/services/architectConversation/` incl. `architectConversationCoordinator.ts`, `questionSequencer.ts`, the `/capture` route). Investigate reuse-vs-fork: target-state is QUESTION-LIBRARY-driven; this is REVIEW-AGENDA-driven — same chassis, different domain driver.
- IR is cited as conversation EVIDENCE (the rich discovery intermediate representation backs the Architect's narration) AND is already suppressed downstream on reject (Spec 2).
- The LLM is an ENHANCEMENT: Specs 0-2 work fully without it; Spec 3 must degrade to the grid if the LLM is unavailable.
- Honor the architecture meta-model (logical↔physical distinct + non-1:1; classes/methods first-class; `*_points` backend-managed). AMS speaks snake_case at the wire by default.
- ORACLE STANDARD throughout (the user's overriding directive): completeness over convenience; no stubbed/deferred required functionality; the Architect must surface the FULL truth (conflicts, cascades, the complete touched set), never a convenient summary that hides richness.

**Open questions for the shaper to resolve with the user include:** the chunking strategy (how the agenda is segmented + ordered — by entity type? by merge group? by interface/blast-radius cluster? conflicts-first? — and chunk size); reuse-vs-fork of the target-state Architect Conversation coordinator (a new review-driven persona/mode in the SAME coordinator + RHS chassis, vs a parallel coordinator sharing the primitives); the exact LLM tool/function surface + the confirmation gate (which calls are read-only vs mutating, and how "confirm before write" is enforced); how the bulk-resolve-by-pattern UX is surfaced conversationally and mapped to the deterministic `resolveConflict`-by-source (Spec 0's similarity class); how the conversation + grid stay in sync (shared React state/context? both re-reading the Spec 1 model after each write?); transcript persistence (the target-state thread storage pattern `{projectParentFolder}/threads/{type}/thread.json`); the RHS "room" naming/placement + entry point (a "Discovery Review Room" launched from the run-detail page?); the LLM relay + model wiring (the existing gateway conversation LLM relay; GPT 5.x); and how much of the conversational UI is net-new vs a thin re-skin of the target-state chassis.
