Spec 4 (final) of a 4-spec migration auto-flow program — "Migration Reconciliation + Bug Loop (the Verification back-half)".

GOAL: After the Migration Execution Driver's FINAL spec deploys (Spec 3's "deployed" build-results callback), run the automated verification/reconciliation half: replay ALL captured current-state operations against the deployed target, flag behavioural BREAKS (any differing response), send them as BUG REPORTS to the external implementation/verification service, and on the fix-redeploy callback RE-RECONCILE only those breaks — with a CIRCUIT BREAKER (no auto-re-report after one failed round → human review). This EXTENDS the build-results door that Spec 3 builds.

KEY WORK:
- EXTEND Spec 3's build-results receiver/dispatch (POST /api/implementation/build-results) with the remaining paths: `deployed` (no bug_id, the final-spec deploy) → trigger FULL reconciliation; `bug_id` + `deployed` → trigger SCOPED re-reconciliation of that bug's breaks; `bug_id` + `failed`/`rejected` → route the break(s) to human review.
- FULL RECONCILIATION TRIGGER: on the final `deployed` callback, drive the Reconciler (the existing api-migration-validation-service) to replay ALL captured current-state operations (the API behaviour baseline) against `target_base_url` (per-project credentials, per-invocation, capture-harness pattern — never stored), structurally diff each response vs the current-state oracle, record BREAKS — EXCLUDING any DEFERRED stories' operations (Spec 3's "defer this story" must be honoured so deferred ops are not false breaks). Then POST the verdict back to the external service's `/api/v2/reconciliation` to RELEASE the haibox serve box (the verdict-round-trip release step the external dev built).
- "SHOW ALL BREAKS" review surface (frontend): every differing response rendered as a break (operation, replayed request, current-state expected, target actual, structured diff), selectable for reporting.
- BREAKS → BUG-REPORT SEND: POST /api/v2/bugs (per-break prose description like "GET /X — current=View2, target=null — investigate" + an optional JSON evidence attachment breaks.json) with Haikai's `callback_url`; persist bug_id → [break ids]. One report per user-selected batch of breaks.
- BREAK↔BUG LIFECYCLE (AMS, new Liquibase changeset after Specs 1/3): states open → reported → (fix_reported → re-run → closed | reopened→needs-review) | needs-review (failed/rejected). Persist bug_id↔break-ids linkage.
- SCOPED RE-RECONCILIATION: on the bug-fix `deployed` callback (bug_id present), replay ONLY that bug's breaks against the redeployed `target_base_url`; close on match, reopen on diff.
- CIRCUIT BREAKER: a re-run that STILL differs → do NOT auto-re-report → mark "needs human review"; bounded to 1 re-run round. Disposition states: closed / needs-review / disputed.
- DISPOSITION UI (frontend): break review + disposition + the needs-review queue.

LOCKED DECISIONS: BIG-BANG (one full reconciliation after the final deploy); Haikai OWNS the replay reconciler (the external service's own reconcile.py is their-side fallback, NOT used in this flow); reconciliation runs only against a DEPLOYED target; per-invocation target credentials stay our side (never stored); circuit breaker = 1 round then human review; deferred stories (Spec 3) are EXCLUDED from reconciliation scope; the verdict-round-trip release POST to the external `/api/v2/reconciliation` releases the haibox box.

OWNERS: gateway (build-results dispatch EXTENSION, reconciliation trigger + verdict-release, bug-report send, scoped re-run, circuit breaker); api-migration-validation-service / the Reconciler (the replay-vs-baseline engine — exists; needs callback-driven trigger + supplied target_base_url + creds); architecture-model-service/AMS (break↔bug lifecycle persistence; new Liquibase changesets ONLY — coordinate numbering after Specs 1/3; snake_case wire; boxed PATCH-mutable types); frontend (breaks review + send-bug + disposition UI).

OUT OF SCOPE: spec generation (Spec 1); TEST items (Spec 2); the Migrate button + Driver + auto-answerer + the build-results DOOR itself (Spec 3 — Spec 4 only EXTENDS it with the deployed/bug_id paths). The external service's bug investigate→fix→redeploy + its CI verification + haibox deploy are already built on their side.

REUSE: the api-migration-validation-service reconciler (replay vs current-state baseline; the capture/replay harness; per-invocation credentials); Spec 3's build-results door (extend, don't rebuild); the existing drift-report / breaks surface; the external service's `POST /api/v2/bugs` + `GET /api/v2/bugs/{bug_id}` + `POST /api/v2/reconciliation` (their side, built); the extractGitOutcome helper; the break/bug persistence patterns.
