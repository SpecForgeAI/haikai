# Spec Requirements: Candidate Review and Approval Workflow

## Initial Description

Increment 13 of 16 for the legacy/current-state discovery capability. Previous increments established the full discovery pipeline (Phase 0 + Phase 1a-1d), candidate generation, controlled save-back to canonical model, and read-only visibility of discovery results. This increment introduces the first user-in-the-loop review workflow for discovery candidates, enabling users to review discovery candidates, approve/reject/defer them, and control what gets persisted into the canonical architecture model. At the end of this increment, users can actively curate discovery outputs and save-back becomes user-governed rather than purely automatic.

## Requirements Discussion

### First Round Questions

**Q1:** I assume the review state fields (status, reviewer, timestamp, previous state) will be added directly to the existing discovery candidate data structure/entity, rather than stored in a separate "review decisions" table or file. Is that correct, or would you prefer a separate audit/review record structure to keep discovery data and review data decoupled?
**Answer:** Store review state directly on the candidate model for this increment; no separate review table needed yet.

**Q2:** I assume that all candidates generated by the existing discovery pipeline (Increments 1-12) will default to pending_review once this increment is deployed, and that no candidates should be grandfathered as approved. Is that correct, or should previously-saved candidates (those already saved back to the canonical model) be retroactively marked approved?
**Answer:** Default all existing candidates to pending_review rather than retroactively approving anything.

**Q3:** The description says automatic save-back from Increment 11 should be "disabled or limited to high-confidence cases." I assume for simplicity in v1 we should fully disable automatic save-back and require all candidates to go through review before save-back. Is that correct, or do you want to preserve automatic save-back for candidates above a certain confidence threshold while gating the rest?
**Answer:** Preserve automatic save-back only for clearly high-confidence cases; everything else should go through review.

**Q4:** I assume users will approve individual candidates one-by-one and then trigger save-back either per-candidate or as a batch of all approved candidates in the current run. Should save-back be triggered as "save all approved candidates in this run" (single button), or should users be able to save-back individual approved candidates selectively?
**Answer:** Start with a simple "save all approved candidates for the run" action; no need for fine-grained per-candidate save yet.

**Q5:** I assume deferred means "skip for now, revisit later" and deferred candidates remain visible in the review list for future runs/sessions. Should deferred candidates carry forward across discovery runs, or should they reset to pending_review when a new discovery run produces updated results for the same candidate?
**Answer:** Treat defer as run-scoped; do not carry it across runs in this increment.

**Q6:** The description calls for basic "who performed the review" attribution. Since the roadmap shows authentication (OAuth2/OIDC) is not yet implemented, I assume "who" will be a simple identifier such as the current session or a user-provided name, rather than an authenticated identity. What should the user identity source be for this audit trail?
**Answer:** Use a simple lightweight identity (e.g., session/user label) consistent with the current system; no full auth model needed.

**Q7:** I assume the review actions (approve/reject/defer buttons) will be added to the existing discovery results visibility view introduced in earlier increments, likely as action buttons on each candidate row or card. Should the review UI be inline in the existing candidate list view, or presented as a dedicated review panel/modal when a candidate is selected?
**Answer:** Use inline actions within the existing candidate list rather than introducing a new dedicated panel.

**Q8:** Is there anything explicitly excluded that I haven't mentioned? For example, should we avoid adding any filtering or sorting by review state in this increment, or is basic filtering (e.g., "show only pending" or "show only approved") considered in scope as part of the minimal UI?
**Answer:** Basic filtering (e.g., pending/approved/rejected) is in scope, but keep it simple.

## Requirements Summary

### Functional Requirements
- Extend the candidate model with a review state field supporting four values: pending_review, approved, rejected, deferred
- All existing candidates (from prior increments) default to pending_review on deployment; nothing is retroactively approved
- Users can perform three review actions on individual candidates: approve, reject, defer
- Review actions update candidate state, are persisted, and are scoped to project and run
- Deferred status is run-scoped and does not carry forward across discovery runs
- Basic filtering by review state (e.g., show only pending, approved, or rejected candidates) is available in the UI
- Automatic save-back from Increment 11 is preserved only for clearly high-confidence candidates; all other candidates require manual review before save-back
- A single "save all approved candidates for this run" action triggers save-back for all approved candidates in the current run (no per-candidate save granularity)
- Save-back remains idempotent even when triggered after review
- Backend endpoints support: updating candidate review state, retrieving candidates with review status, and triggering save-back for approved candidates
- Lightweight audit trail captures: who performed the action (session/user label), when it was performed, and previous state
- State transitions are explicit and traceable

### Reusability Opportunities
- Existing discovery candidate list/visibility views from earlier increments should be extended with inline review actions
- Existing save-back mechanism from Increment 11 should be modified to gate on review state
- Existing candidate model/entity should be extended rather than replaced
- Existing backend discovery endpoints should be extended with review-related operations

### Scope Boundaries

**In Scope:**
- Candidate review states: pending_review, approved, rejected, deferred
- Review actions: approve, reject, defer (inline in existing candidate list)
- Review state persistence (directly on candidate model)
- Gating save-back by review state (approved candidates only for manual trigger; high-confidence for automatic)
- Batch save-back trigger for all approved candidates in a run
- Backend endpoints for review actions, candidate retrieval with status, and save-back trigger
- Basic filtering by review state in the UI
- Lightweight audit trail (who/when/previous state) using session-based identity
- Run-scoped defer behavior

**Out of Scope:**
- Bulk editing or advanced filtering UX
- Editing candidate details (rename, retype, re-parent)
- Multi-user collaboration or conflict resolution
- Advanced approval workflows (multi-stage, role-based)
- Deep evidence inspection UI
- Log-based enrichment
- AST enrichment
- Language/version-specific analyzer packs
- Per-candidate selective save-back
- Carrying deferred state across runs
- Separate review/audit table (review state stored on candidate model)
- Full authentication-based identity for audit attribution

### Technical Considerations
- Review state is stored directly on the candidate model/entity, not in a separate table
- Backend endpoints must be idempotent
- All operations are scoped to project and run
- User identity for audit is lightweight (session/user label), not authenticated identity
- Automatic save-back behavior from Increment 11 must be conditionally preserved for high-confidence cases, requiring a confidence threshold mechanism
- The definition of "clearly high-confidence" for automatic save-back needs to be determined during implementation (likely based on existing confidence scoring from earlier increments)
- This increment enables Increment 14 (log-based discovery enrichment) and Increment 15 (hypothesis-first discovery and Q&A)
