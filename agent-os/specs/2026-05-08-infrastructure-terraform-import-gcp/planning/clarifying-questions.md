## Numbered Questions

### 1. HCL parser choice

The backend is Spring Boot / Java 21 with no HCL dependency today. We have three realistic options, each with trade-offs:

  **(a) Vendor an existing Java HCL parser** (e.g. `com.bertramlabs.plugins:hcl4j` — Apache 2.0, supports HCL2, used in some cloud-cost tools). Pros: fastest path, handles real-world `.tf` files including comments, `for_each`, dynamic blocks. Cons: adds a Maven dep; need to confirm Maven Central availability + offline-build behaviour; license review.

  **(b) Hand-roll a tolerant subset parser** scoped to: top-level `resource`, `module`, `variable`, `output`, `locals`, `provider` blocks; literal string / number / bool / list / map values; simple `var.foo` and `<resource>.<name>.<attr>` references; preserves unknown expressions verbatim as raw strings. Pros: zero new deps, fully under our control, naturally tolerant. Cons: ~600-1000 LOC including line-tracking, will not handle every real-world Terraform but matches the scope explicitly listed in the raw idea ("complex expressions preserved as raw text/evidence").

  **(c) ANTLR-based parser** with a Terraform-HCL grammar. Pros: clean, formal grammar, line/column info for free. Cons: adds antlr-runtime dep, grammar maintenance, slower to ship.

  **My assumption: (b) hand-rolled tolerant subset parser** — it matches the explicit raw-idea scope ("Full Terraform expression evaluation is out of scope. Complex expressions should be preserved as raw text/evidence where possible"), keeps `pom.xml` zero-new-deps consistent with the export spec's locked contract, and avoids any offline-build risk. Is that what you want, or do you prefer (a) or (c)?

### 2. Candidate persistence model

The discovery-service has a long-lived **runs table** with rows persisted in the architecture-model-service DB (`discovery_runs`, `discovery_candidates`, `discovery_evidence`, `discovery_decision_tasks`). The export spec, by contrast, is **transient** — it generates a ZIP in-memory, dual-writes files to disk, and returns. Three options:

  **(a) Persistent import-run rows** — new tables `terraform_import_runs`, `terraform_import_candidates`, `terraform_import_evidence`, `terraform_import_decisions`. Re-uses the discovery pattern. Heavier (Liquibase changesets, repositories, services, lifecycle).

  **(b) Transient — single API round-trip.** User uploads, backend parses + classifies + returns the entire candidate review payload in the response. Frontend holds it in React state; user reviews and submits the approved subset back as a model save. No DB rows for the import itself. Lightest. Loses session if user closes the tab mid-review.

  **(c) Filesystem-backed** — mirror the export pattern: write the parsed candidate review JSON to `{projectParentFolder}/imports/terraform/<timestamp>/candidates.json` as the source of truth. No DB rows; user can re-open a recent import by browsing the folder. Mid-weight.

  **My assumption: (b) transient single round-trip for V1**, with the caveat that approve-into-model is a separate explicit user action (so even if the page reloads, no model mutation has happened — they just lose the staged review). This matches the export spec's transient pattern, ships fastest, and the raw idea's fallback ("If no existing review UI is reusable, show the import result in a simple review table and defer advanced approval workflow to a later spec") explicitly allows it. Persistent runs can be a follow-up spec when discovery-service-style integration matures. OK to lock as (b)?

### 3. Where in the UI

Candidates:

  **(a) FileMenu — same Export group.** Add "Import Infrastructure from Terraform..." next to "Export Infrastructure as Terraform...". Symmetric, discoverable in the same place.

  **(b) Infrastructure domain header / table tab action.** Lives where users edit Infrastructure entities (closer to where the resulting candidates would land).

  **(c) Both.** FileMenu for the global discovery path + a context-menu shortcut from any Infrastructure tab.

  **My assumption: (a) FileMenu, parallel to the export entry**, identical pattern (gated on `model loaded AND at least one Environment exists`). Easiest to wire (one new menu prop + one new modal), preserves visual symmetry with the export. Is that right, or do you want (b) or (c)?

### 4. Multi-file / ZIP semantics

When the user uploads a ZIP with multiple `.tf` files (and possibly subdirectories — e.g. a Terraform repo with `modules/network/`, `modules/compute/`, `environments/prod/`):

  **(a) Whole-ZIP-is-one-IaCSource.** Every `.tf` file inside the ZIP is parsed; every resource block becomes a candidate; `file_path` on each binding is the ZIP-relative path. One proposed `IaCSource` carries all bindings. Module bodies are parsed only when literal HCL files are present in the ZIP; remote modules are skipped with a warning.

  **(b) Each subdirectory = one IaCSource.** Walks the tree, treats each leaf directory containing `.tf` files as a separate `IaCSource`. More granular but heavier UI; a single ZIP could propose 5+ IaC Sources.

  **(c) Each `.tf` file = one IaCSource.** Even more granular; usually wrong because real Terraform splits state by directory not by file.

  **My assumption: (a) whole-ZIP-is-one-IaCSource for V1**, with `file_path` recorded relative to the ZIP root (e.g. `modules/network/main.tf`). Module bodies parsed only if their files are literally inside the uploaded payload (relative `source = "./modules/network"` works; `source = "git::https://..."` triggers a soft-warn TODO). One IaC Source per upload. The user can run multiple imports if they have multiple workspaces. Is that right?

### 5. Variable / locals / module expansion — V1 cut

The raw idea says "Full variable interpolation resolution is out of scope. Complex expressions should be preserved as raw text/evidence where possible." That leaves choices about how aggressive V1 is:

  **(a) Strict literal-only.** If a field is `var.region`, `local.env`, or any reference at all, leave the field unresolved on the candidate and surface a TODO with the raw expression as evidence. No interpolation.

  **(b) Resolve-when-default-is-literal.** If `var.region` is declared with `default = "europe-west1"`, resolve it. If no default, leave as raw `var.region` + TODO. If the user-supplied import options include explicit values (e.g. they typed `region = europe-west1`), prefer those over defaults.

  **(c) Best-effort — try literals + defaults + user-provided + simple `local.x = "y"` lookups.** No iteration / no `for_each` / no template strings — but follow one hop of `var` and `local`.

  **My assumption: (c) best-effort** — resolve in order: user-provided import options > variable defaults > simple `local = "literal"` definitions. Anything beyond one hop, or any expression involving `for_each` / `count` / template strings / function calls, is preserved verbatim as evidence and surfaces a TODO. Module bodies (referenced via `module "x" { source = "./..." }`): V1 parses the module's HCL files when present in the upload payload, but does NOT do parameter substitution into module variables — the module's own resources land as separate candidates with `file_path` pointing at the module HCL, and a comment trail noting the calling module. Is that the right cut?

### 6. Deterministic matching — tie-breaker when iac_address matches but name was edited

The raw idea says "Attempt deterministic matching before creating new candidates: existing IaC Resource Binding by iac_address ... If a match is found, propose update/merge candidate rather than duplicate entity." Question: when the binding's `iac_address` matches but the user has edited the entity's `name` (or other field) since the last import:

  **(a) Imported value wins.** Re-sync proposes the imported name; user-edited name is overwritten on approval. Predictable, matches "source of truth = Terraform" semantics.

  **(b) User-edited value wins.** Manual edits are preserved; importer surfaces the divergence in the candidate ("Name in Terraform: `prod-vpc`; current model name: `Production VPC` (manually edited)") but proposes no change to that specific field. Other fields still re-sync where unedited.

  **(c) Per-field manual review.** Every divergent field appears as a side-by-side diff in the candidate; user picks left/right per field on approval.

  **My assumption: (b) user-edited wins for `name` and `description`; imported wins for everything else.** Field-level: name/description are the human-readable labels users curate. The CIDR / region / engine / type fields are derived facts that should re-sync. The candidate review UI surfaces ALL diverging fields (left = current model, right = imported) but the proposed update only mutates the non-name/description fields. The user can override the per-field default via the candidate review (this is just the **default proposal**). Is that the right balance?

### 7. Approval granularity + "ignore" semantics

  **(a) All-or-nothing per import run.** User clicks "Approve all" or "Discard all". Simplest; matches the export spec's flat shape.

  **(b) Per entity type.** "Approve all networks", "Approve all compute resources", etc. Mid-weight.

  **(c) Per individual candidate.** Checkbox on every row in the review table. Heaviest UI but highest user control.

And separately, what does **"ignore"** mean:

  **(i) Soft-hide-from-this-run only.** Future imports re-propose the same candidate.

  **(ii) Persisted "rejected" record** stored alongside the IaC binding — future imports of the same `iac_address` see the prior rejection and either skip or propose with an "previously ignored" flag.

  **My assumption: (c) per-individual-candidate approve/ignore for V1, with (i) soft-hide-from-this-run-only semantics.** Per-row control matches the discovery candidate-review UI pattern users already see; soft-hide keeps V1 storage trivial (no new "rejected" table) and matches the raw idea's "create reviewable candidates, not directly update". Persisted rejection state is a follow-up spec. Bulk "select all in this group" buttons on the review modal as a UX nicety. Sound right?

### 8. Confidence scoring — bucket vs numeric

The IaC Resource Binding entity already has `confidence DECIMAL(4,3)` from the readiness spec. For V1 import:

  **(a) Three fixed buckets — HIGH (0.90) / MEDIUM (0.60) / LOW (0.30).** Easy to display, easy to explain. Stored as decimal but only ever takes one of three values in V1.

  **(b) Numeric 0–1 score** computed deterministically from a small set of signals (resource type known, all references resolved, env/region inferred, file_path + start_line captured, etc.). Each signal is +0.x.

  **(c) Boolean-style — 1.0 if mapped, soft-warn otherwise.** Crude.

  **Signals that feed scoring** (for either (a) or (b)):
  - resource type is in the GCP mapping table (+major)
  - all variable references resolved to literals (+)
  - environment / region inferred deterministically (+)
  - exact file_path + start_line + end_line captured (+)
  - matches an existing iac_address binding (+major if matched, neutral if new)
  - LB composite is complete (all 5 resources present) (+)
  - referenced subnet/network/etc. found in same upload (+)

  **My assumption: (a) three fixed buckets in V1**, with the bucket chosen via a simple rule:
  - HIGH: resource type in mapping table + zero unresolved references + env/region inferred or user-provided
  - MEDIUM: resource type in mapping table BUT some references unresolved OR env/region not inferred
  - LOW: resource type unknown or partial mapping (e.g. LB composite missing pieces)

  Is the (a) three-bucket cut acceptable, or do you want (b) numeric scoring from V1?

### 9. LB composite handling — V1 mandatory or V1 optional

GCP load balancers are composite resources: `forwarding_rule` + `backend_service` + `url_map` + `target_*_proxy` + (NEG for Cloud Run) — typically 4-5 separate Terraform resources that together form ONE high-level `LoadBalancer` entity in our model.

  **(a) V1 mandatory composite grouping.** Importer detects all 5 components, groups them into one `LoadBalancer` candidate, derives the `Listener` from the URL-map host/path rules. Hard work — needs reference resolution across resources, partial-match handling. If pieces are missing, soft-warn but still produce one composite candidate.

  **(b) V1 optional — emit each LB component as its own infrastructure-resource-style candidate** with a TODO "this looks like part of a composite LB; consider creating a parent LoadBalancer entity manually". Defer real grouping to a later spec. Lighter; ships faster.

  **(c) V1 mandatory but with a fallback** — try composite grouping; if more than one component is missing, fall back to (b) per-component candidates plus an "unrecognised-LB-pattern" warning.

  **My assumption: (c) — try composite grouping, fall back to per-component candidates with a warning when pieces are missing.** This honours the raw idea's "Produce a readable candidate and warnings when only partial LB structure is understood" without making the grouping algorithm so demanding that any non-textbook LB blows up the importer. The export-spec dual already locks the composite shape (5 resources mapped to one Load Balancer + one Listener), so the import inverter knows the canonical shape to look for. Sound?

### 10. Tests — round-trip golden fixture

The export spec has a golden-file snapshot test (`TerraformExportGoldenFileTest`) that asserts byte-for-byte the output of a 7-entity input model. For the import side:

  **(a) Round-trip golden.** New test `TerraformImportRoundTripTest` that feeds the EXPORT spec's golden `expected/main.tf` (+ `variables.tf`, `outputs.tf`) into the importer and asserts the resulting candidate set, when approved, would re-produce the same Infrastructure entities the export started from. Strong contract test; the tightest possible round-trip stability guarantee.

  **(b) Forward-only golden.** New test that takes a hand-written Terraform fixture (e.g. `src/test/resources/terraform-import/input.tf`) and asserts the candidate JSON byte-equal against a committed `expected-candidates.json`.

  **(c) Both.** Forward fixture for raw input variety + round-trip fixture for contract symmetry.

  **My assumption: (c) both.** The forward fixture covers cases the export wouldn't naturally produce (raw HCL with comments, unresolved variables, unsupported resource types — exercising warning paths). The round-trip fixture pins the export↔import contract symmetry: same `iac_address` values come back in the bindings, same entity names, same field values. Round-trip is intentionally on the export's golden HCL files (not a separately maintained import fixture) so the two specs stay in sync. Sound?

### 11. Frontend review UI — full vs deferred

The raw idea explicitly allows the fallback: "If no existing review UI is reusable, show the import result in a simple review table and defer advanced approval workflow to a later spec."

  **(a) Full review modal.** Per-candidate approve/ignore, side-by-side diff for matching candidates, evidence drill-down (file path + line range + raw HCL snippet), bulk actions, confidence display, warnings panel. Mirrors the discovery-service candidate-review UI.

  **(b) Deferred — read-only summary table.** Modal shows the parsed candidates as a table (entity type, name, source file:line, confidence, warnings). Single "Approve all" + "Discard all" buttons. No per-row controls. Faster to ship; raw idea's explicit fallback.

  **(c) Hybrid — read-only table + "Open detailed review" button** that opens a richer side-panel (deferred to future spec; button is greyed-out + "Coming soon" in V1).

  **My assumption: (b) deferred read-only summary table for V1**, with all-or-nothing approve. Rationale: the discovery candidate-review UI exists but is wired to discovery-service runs (DB-backed), not to a transient import payload — wiring it to a transient response would be a substantial refactor on its own. (b) ships the import end-to-end without that detour. The raw idea explicitly permits this. (c) is what we'd want eventually but is not essential for the first release. Per-candidate approve/ignore returns in a follow-up spec when (Q2-style) persistent runs land. Is (b) the right V1 cut, or do you want (a) full review now?

### 12. LLM enrichment — V1 deterministic-only or behind a flag

The raw idea says: "Prefer deterministic parsing and mapping first. Use LLM assistance only for enrichment/suggestions where existing system patterns support it. LLM must not be required for basic import to function."

  **(a) V1 deterministic-only.** No LLM at all in the V1 import path. LLM hooks are deferred to a follow-up spec.

  **(b) V1 with optional LLM enrichment behind a feature flag** (`infrastructure.terraform.import.llm.enabled = false` by default). When on, LLM is asked to suggest naming cleanup / explain unsupported resources / group ambiguous LB components. When off, importer behaves exactly like (a). LLM output ALWAYS shown as advisory text on the candidate, never auto-applied.

  **(c) V1 with mandatory LLM enrichment** — bad idea given the constraint, ruling out.

  **My assumption: (a) V1 deterministic-only.** Matches the export spec ("No LLM-based generation — hand-rolled string-fragment emitters only"), keeps the V1 surface small, and the raw idea is explicit that "LLM must not be required". Adding the flag in (b) is cheap but introduces config + test surface for a feature we can ship later. Defer LLM to a follow-up spec when the deterministic baseline is locked. Is (a) the right V1 cut?

## Existing Code Reuse

The spec-shaper has already identified the following existing-code reuse opportunities (these will be referenced in the spec):

- **Symmetric pair to the export package** — `architecture-model-service/src/main/java/com/example/architecturemodel/service/export/terraform/`. The import will live in a sibling package `service/import/terraform/` with mirrored shapes (`TerraformImporter` strategy interface, `GcpTerraformImporter` impl, `TerraformImportContext`, `TerraformImportService`).
- **Controller pattern** — `InfrastructureTerraformExportController` is the verbatim template for the new `InfrastructureTerraformImportController` (also new file, not folded into `ModelController`).
- **Frontend modal pattern** — `frontend/src/components/Export/InfrastructureTerraformExportModal.tsx` (and its `.module.css`) is the verbatim template for the new `InfrastructureTerraformImportModal.tsx`. The provider dropdown reuses `iacSourceProviderOptions` from `defaults.ts:1321` (do NOT redeclare).
- **FileMenu wiring pattern** — the existing `onExportInfrastructureTerraform` / `exportInfrastructureTerraformDisabled` props in `FileMenu.tsx` are the verbatim template for `onImportInfrastructureTerraform` / `importInfrastructureTerraformDisabled`.
- **API helper pattern** — `modelApi.exportInfrastructureTerraform(...)` is the template for `modelApi.importInfrastructureTerraform(projectId, architectureId, formData)`. Probably a `POST` with `multipart/form-data` for the file upload.
- **Mapping table** — `GcpTerraformExporter` and the export `spec.md` define the GCP-resource ↔ Infrastructure-entity mapping. The importer must REVERSE this mapping (e.g. `google_compute_network` → `Network`; `google_cloud_run_v2_service` → `ComputeResource (CLOUD_RUN_SERVICE)` plus implicit `ComputeCluster (CLOUD_RUN)`).
- **`IaCSource` + `IaCResourceBinding` entity shapes** — already landed by the readiness spec. Importer creates instances of these. `iac_address` must be persisted EXACTLY as parsed (round-trip stability with export).
- **Provenance fields on Infrastructure entities** — `source_origin`, `source_system`, `source_reference`, `last_verified_at`. Importer sets these to `'IMPORTED'`, `'terraform-import'`, `'<iac_address>'`, current timestamp.
- **`InfrastructurePoint` polymorphic point pattern** — `IaCResourceBinding.infrastructure_point_id` resolves to the appropriate Infra entity via the `target_type` discriminator.
- **`iacSourceProviderOptions` picklist** — already in `defaults.ts:1321` and mirrored backend-side in `TerraformExportService.PROVIDER_OPTIONS`. Reused as-is.
- **Discovery-service candidate review pattern** — `discovery-service/src/services/runManager.ts` shows the full run row → candidates → evidence → triage → DecisionTask → approve flow. NOT being directly reused in V1 (Q2/Q11 above), but documented as the canonical pattern the import would migrate to in a later spec.

If you have additional file-paths or pattern names you'd like the spec-writer to reference (e.g. a specific test you want mirrored, or a specific component you'd like the import modal styled after), please call them out.
