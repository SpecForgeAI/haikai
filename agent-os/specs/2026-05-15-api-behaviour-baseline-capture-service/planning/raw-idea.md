Feature name:
API Behaviour Baseline Capture Service

Service name:
api-migration-validation-service

Feature summary:
Add a new microservice and supporting platform capability to capture API behaviour baselines from a current-state deployed non-prod service. The service uses supplied OAS specs, current-state architecture context, configured API environment/auth details, optional read-only Sybase/PostgreSQL database sampling, and an LLM-guided capture loop to generate and execute API requests. Successful or meaningful captured request/response examples are reviewed by the user and saved as a durable API Behaviour Baseline.

This baseline will later be used by migration planning, target-state implementation backlog generation, Migration Test Pack creation, and a future API reconciliation/reporting capability.

Primary user:
Architect, Test Engineer, or migration planner preparing for a functionally equivalent current-to-target migration.

Business goal:
Capture evidence of how current-state APIs behave so future target-state implementation and migration validation can prove functional equivalence using real request/response examples.

Core assumption:
For v1, current and target APIs are expected to preserve the same API contracts. OAS specs are provided by the user or generated by the existing OAS task.

V1 scope:
- New api-migration-validation-service.
- OAS 3.x parsing for REST APIs.
- Upload/select OAS specs for current-state APIs.
- Configure current non-prod API base URL and auth.
- Allow all HTTP verbs only after explicit mutating-call confirmation.
- Optional read-only Sybase/PostgreSQL DB sampling.
- LLM-guided request/scenario generation through constrained tool calls only.
- Execute generated requests against current non-prod API.
- Bounded retry/refine on failures.
- Store draft captures and failure diagnostics.
- Review captured request/response examples.
- Persist accepted examples as API Behaviour Baseline in AMS.
- Use gateway/shared LLM abstraction where feasible.
- Anticipate future reconciliation in data model but do not implement.

Out of scope for v1:
- API reconciliation against target service.
- DB reconciliation, data migration, proxy/log capture, OAS generation, migration roadmap/backlog generation, full business-rule equivalence proof.
- DB engines beyond Sybase/PostgreSQL.
- Free-form unrestricted SQL.
- Production API/DB execution.

High-level flow:
1. User starts capture session.
2. Selects Current State Architecture.
3. Uploads/selects OAS spec(s).
4. Configures non-prod API env (base URL, auth, headers, timeout/retry).
5. Optionally configures read-only DB connection (type, host/port/db/schema, creds, allowlists).
6. Confirms env safe for mutating calls.
7. Service parses OAS into operation inventory.
8. User reviews included/excluded operations.
9. LLM-guided capture loop runs (scenarios, OAS examples, DB samples, candidate requests, retries).
10. Service stores draft captures + diagnostics.
11. UI presents endpoint/scenario review.
12. User accepts/rejects/renames/annotates.
13. Accepted captures saved as API Behaviour Baseline records in AMS.
14. Baseline available to future migration-planning and reconciliation features.

Architecture:

api-migration-validation-service responsibilities:
- OAS parsing/orchestration; capture session execution; LLM-guided generation; HTTP execution; optional read-only DB sampling; retry/refinement; redaction/masking; calls AMS to persist sessions, scenarios, captures, diagnostics, accepted baselines.

AMS responsibilities:
- Durable persistence for capture sessions and API Behaviour Baselines.
- CRUD/search for baselines, scenarios, captures, diagnostics.
- Project/architecture/interface association.
- Persistence model anticipates future reconciliation runs.

Gateway responsibilities:
- Proxy frontend → AMS and api-migration-validation-service.
- Provide/proxy shared LLM access.
- Owns no durable baseline data.

Frontend responsibilities:
- Setup wizard, OAS upload, env/auth UI, optional DB UI, endpoint inclusion review, capture progress, results review, accept/reject/edit, save baseline.

AMS data model (7 tables):
1. `api_behaviour_capture_sessions` — id, project_id, architecture_id, name, status (draft/configured/running/completed/failed/cancelled), env_name, api_base_url, auth_type, auth_config_redacted_json, default_headers_redacted_json, oas_spec_refs_json, db_config_redacted_json?, mutating_calls_confirmed, timestamps, started_at?, completed_at?, error_message?
2. `api_behaviour_operations` — id, session_id, operation_id?, method, path, summary?, description?, included, safe_to_execute, request_schema_json?, response_schema_json?, oas_operation_json, timestamps
3. `api_behaviour_scenarios` — id, session_id, operation_id, scenario_name, scenario_type (happy_path/not_found/validation_error/empty_result/boundary_value/auth_error/business_edge_case/generated_candidate), status (draft/executed_success/executed_error/accepted/rejected/needs_review), generation_source (oas_example/db_sample/llm_generated/llm_refined/user_edited), request_method, request_path, request_query_json?, request_headers_redacted_json?, request_body_json?, notes?, timestamps
4. `api_behaviour_captures` — id, session_id, scenario_id, operation_id, attempt_number, request_*, response_status?, response_headers_redacted_json?, response_body_json?, duration_ms?, error_type?, error_message?, captured_at, accepted, accepted_at?, reviewer_notes?
5. `api_behaviour_diagnostics` — id, session_id, operation_id?, scenario_id?, diagnostic_type (failed_request/auth_failure/db_sample_failure/llm_generation_failure/redaction_warning/endpoint_skipped/retry_exhausted), message, detail_json?, created_at
6. `api_behaviour_baselines` — id, project_id, architecture_id, session_id, name, status (draft/active/archived), timestamps, accepted_capture_count, operation_count, notes?
7. `api_behaviour_baseline_items` — id, baseline_id, capture_id, operation_id, scenario_id, method, path, scenario_name, request_json, response_status, response_json, business_notes?, timestamps

Security & secrets:
- Secrets never displayed back in full after entry.
- Redact auth headers/cookies/keys/passwords/tokens from logs and stored metadata.
- Persist only redacted auth config in AMS.
- Use existing secret/encryption support if present; otherwise document TODO + at minimum redact from UI/logs.
- Capture service must NOT log raw secrets.

API env config:
- Auth types: none, bearer, API key header, basic, custom headers
- Fields: environmentName, baseUrl, authType, authConfig, defaultHeaders, timeoutSeconds, maxRetriesPerScenario, mutatingCallsConfirmed
- Mutating-call confirmation copy: "I confirm this is a non-prod migration-test environment and mutating API calls are allowed."
- Without confirmation: only safe read methods (GET/HEAD/OPTIONS) run; mutating ops excluded.

OAS parsing:
- Parse OAS 3.x; extract operationId, method, path, parameters, requestBody schema, response schemas, examples, security requirements, tags, summaries/descriptions.
- Store inventory in AMS.
- Allow user to include/exclude before execution.
- Default include all only after mutating-call confirmation; otherwise include GET/HEAD/OPTIONS by default and mark mutating ops excluded.

LLM-guided capture loop:
- LLM proposes scenarios, candidate values, DB sampling needs, parameter↔column mappings, interprets failed responses, proposes bounded refinements, generates scenario names + business notes.
- LLM does NOT directly execute network calls or SQL.
- LLM calls constrained tools: list_oas_operations, get_oas_operation_detail, list_db_metadata, sample_db_values, run_readonly_sql, execute_http_request, record_scenario_candidate, record_capture_note.

Tool guardrails:
- execute_http_request: only included OAS operations; injects auth securely; timeout + retry limits.
- run_readonly_sql: SELECT only; blocks INSERT/UPDATE/DELETE/MERGE/DROP/ALTER/TRUNCATE/EXEC/CALL/stored procedures/multi-statement SQL; row limits + timeouts.
- sample_db_values: generated safe SELECTs only.
- All outputs redacted before persistence.

DB sampling:
- v1: Sybase + PostgreSQL only.
- Read-only sampling only — no mutate, migrate, compare, stored procs, or destructive SQL.
- DB config: dbType, host, port, databaseName, schemaName?, username, password, connectionOptions?, allowlistedSchemas?, allowlistedTables?, maxRowsPerQuery, queryTimeoutSeconds.
- Examples: sample IDs for path params, enum/code values, date ranges, search criteria.
- DB-specific query builders where possible.
- Always row limit + timeout.
- Prefer allowlisted schemas/tables.
- Persist sampled values only when needed for request gen, after masking.

Request generation:
1. Base scenario templates per OAS operation.
2. OAS examples first.
3. DB samples for path/query/body where possible.
4. LLM fills remaining required values.
5. Execute candidate request.
6. If success or meaningful error, keep as draft capture.
7. If unexpected failure, LLM proposes bounded refinement.
8. Retry to max attempts.
9. Failed attempts → diagnostics, not baseline items unless user accepts.

Default target: 1–3 useful accepted examples per endpoint (happy path + meaningful error/edge cases).

Retry/refinement:
- 404 → alt sampled IDs or generate not-found scenario.
- 400 → adjust required fields/enums/dates/body shape.
- 401/403 → stop + flag auth.
- 500 → diagnostic; retry only if safe.
- timeout → retry within limit, then diagnostic.

Redaction & masking:
- Redact Authorization, Cookie, Set-Cookie, API keys, passwords, tokens.
- Configurable JSON field masking; defaults: password, token, secret, apiKey, authorization, ssn, nationalInsuranceNumber, creditCardNumber, iban; email optional.
- UI allows user to mask additional fields during review.
- Redaction before AMS storage where possible.

Frontend:
- Entry point: "Capture API Behaviour Baseline" — suggested locations: architecture API/interface area, testing/migration prep area.
- 5-step wizard: select architecture+OAS → API env → optional DB sampling → endpoint inclusion/exclusion → start capture summary.
- Capture progress UI: counts, current op, cancel.
- Results review: endpoint summary table (method, path, included/excluded, captured/failed counts, coverage status, warnings) + scenario detail panel + actions (accept/reject/rename/notes/mask/important/rerun/exclude-op).
- Coverage statuses: no_examples, happy_path_captured, error_case_captured, ready, needs_review, excluded.
- Save baseline with name + warnings on uncovered ops.

Acceptance criteria: 23 items covering session creation, OAS upload/parse, env/auth config, mutating confirmation, all HTTP verbs after confirmation, optional DB sampling, read-only safety, LLM via constrained tools only, non-SELECT blocking, secret redaction, request execution, retry/refine, draft capture vs diagnostics, review UX, accept/reject/rename/annotate/mask, AMS persistence, baseline queryable, future-reconciliation-ready data model.

Implementation notes:
- api-migration-validation-service stays focused on execution/orchestration.
- AMS stays the durable system of record.
- Use existing gateway/shared LLM abstraction where feasible.
- LLM = suggestions/plans only; not authority for unrestricted action.
- Capture loop resumable where practical; full resumability not mandatory for v1.
- Service generates request bodies from OAS+DB+LLM; users don't hand-author.
- Endpoint-first scenario-focused review UX.
- JSON storage for request/response payloads.
- Large response bodies have size limits / truncation rules.
- Store enough metadata for future replay against target API.
- Future API Reconciliation Report Service is a separate spec.
