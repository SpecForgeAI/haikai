# Task Breakdown: Two-Phase Migration Delivery Plan Generation (Skeleton → Expand)

## Overview

Total Tasks: 6 task groups (40 sub-tasks)

Split migration delivery plan generation into a phase-1 skeleton (initiative →
epic → feature, no stories) generated by the existing wizard Generate path, and
a user-triggered phase-2 per-epic expansion in the review workspace, with
deterministic inventory batching, template + exception stamping, and 4-layer
verification — so every individual LLM call stays comfortably under the Azure
OpenAI relay's hard ~300s request cap regardless of inventory size.

**Cross-cutting constraints (apply to every group):**

- **NO Liquibase / AMS schema change.** No new columns, no new
  `chk_gmbw_status` values. Per-epic expansion state rides INSIDE the
  `book_of_work_json` jsonb column.
- **Hard env-tunability requirement (user emphasis, verbatim):** the number of
  concurrent LLM requests MUST be configurable via env alone —
  `MIGRATION_PLAN_LLM_CONCURRENCY` default 4, tunable down to 1 (fully serial)
  WITHOUT a code change. `MIGRATION_PLAN_EXPANSION_BATCH_SIZE` default 12.
  ONE pool instance shared across phase 1 AND all of phase 2.
- **The legacy no-streams-selected combined path is untouched** — it keeps
  producing a full single-call plan (back-compat, including its existing
  single-call invariant tests).
- **Layer 4 of verification is the existing downstream shape-spec stage** —
  cite it in code comments as the implementation-correctness safety net; build
  NOTHING for it.
- Builds directly on the per-stream split in
  `gateway/src/services/migrationBookOfWorkHandler.ts` (2026-06-11,
  uncommitted) — extend it, never build parallel machinery.

## Notes

- **Three test stacks:** gateway = Jest (`gateway/src/__tests__/`), AMS =
  JUnit (`mvn test -Dtest=...`), frontend = Vitest (co-located `__tests__/`).
  Each group runs ONLY its own newly-written tests (plus the named existing
  handler suites where a group modifies their subject); never whole suites.
- **One JSON shape for expansion state**, defined once (Group 3.3, shared
  with Group 2's merge and Group 5's types) — the draft document in
  `book_of_work_json` is the single source of truth for resume/retry.
- **Concurrency knob is a hard user requirement:** behaviour against the
  internal relay is unknown; `MIGRATION_PLAN_LLM_CONCURRENCY=1` must yield
  fully serial execution with env change alone.
- **The ~300s relay cap is assumed, not worked around** — batching + stamping
  exist so every individual call (skeleton-per-stream, expansion-per-batch,
  judge-per-batch, bespoke rewrite) fits comfortably under it.
- **Out of scope (do not touch):** downstream shape-spec stage, Jira upload,
  the legacy combined path's behaviour, per-story regeneration UI beyond the
  existing item drawer, any Liquibase change, re-expanding `expanded` epics,
  SSE/streaming progress, `migrationDiscoveryContextClient`, any
  general-purpose job/queue framework.
- **Frontend `tsc` baseline:** verify net-zero NEW errors per group; do NOT
  chase the large pre-existing baseline.
- Group 4 is the largest group by design — the pipeline stages (batching →
  stamping → verification → append) are tightly coupled per epic and atomic
  per epic, so splitting them across groups would force half-built
  intermediate states.
