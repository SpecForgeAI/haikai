"Spec 0" — the second of a 5-spec program (Spec F done → **Spec 0** → 1 → 2 → 3) that unifies + aggregates discovery review and adds a conversational "Architect" review persona. See memory `project_discovery_review_unification_program`.

PROBLEM (confirmed by direct code reading): when discovery scans a codebase, multiple "packs"/sources each emit a candidate for the SAME real architecture element, so the user sees duplicates. Concrete confirmed example: a Java 8 / Spring Classic app produced 3 candidates for every 1 real endpoint — (a) REST-WADL-PACK endpoint under a generic parent interface, (b) REST-WADL-PACK endpoint with no parent, (c) SPRING-CLASSIC-JAXRS endpoint under the specific controller-class interface. 45 real endpoints → 90 WADL + 45 JAX-RS = 135 candidates. Each source holds a DIFFERENT slice of the truth: WADL has verb+path+description (generic interface, no request/response bodies); JAX-RS has the specific controller interface + request/response logical-data-entities + consumes/produces media types BUT its verb/path silently vanish at save.

ROOT CAUSE #1 (dedup keys on parent): `discovery-service/src/services/packPostProcess.ts` `buildEntityAwareDedupKey` keys endpoints as `endpoints | verb | path | parentInterface` and `dedupPackCandidates` DROPS first-wins. Because `parentInterface` is in the key, the same (verb, path) under different parents (generic WADL iface / none / specific controller) lands under different keys and never collapses. Within-set only; no cross-pack/cross-source reconciliation exists today.

ROOT CAUSE #2 (field-name mismatch drops attributes at save): `mcp-server/src/services/candidateSaveBackService.ts` (~lines 1077-1078) maps `entity.operation_verb = data.http_method || data.operation_verb` and `entity.path_or_address = data.path || data.path_or_address`. The JAX-RS detector (`extensionPacks/frameworkAdapters/springClassic/inboundSurfaceDetectors.ts`) writes `data.httpMethod` / `data.fullPath` (camelCase) — NOT read — so JAX-RS endpoints persist with empty verb/path. WADL (`findings/packFindingScanners/contractCandidates.ts`) writes `operation_verb`/`path_or_address` (read fine) but forms no request/response logical-data-entities.

GOAL: replace the parent-inclusive DROP with an identity-keyed MERGE that runs across ALL sources (framework packs, contract passes, runtime evidence Stage 2.5, LLM gap-fill Stage 3). One clean candidate per real element, aggregating attribute-level findings from every source: e.g. one endpoint with verb+path (WADL) + the specific controller interface + request/response logical-data-entities + media types (JAX-RS). Universal — every candidate type, not just endpoints.

LOCKED DECISIONS (from the shaping conversation):
- UNIVERSAL: all candidate types + all sources flow through ONE identity-keyed merge. Per-type identity keys, meta-model-aware (endpoints = HTTP method + OAS/Swagger-normalized path template, `{param}` names collapsed to positional so `{theString}`≡`{myString}`, static vs templated segments distinct; interfaces / logical-data-entities / physical-data-entities / services etc. each get an identity key the spec defines).
- KEEP single-source candidates (found by only one source), marked with provenance.
- AGGREGATE attribute-level: union attributes, NORMALIZE field names to what the save-back reads (fix root cause #2: normalize in the merge AND have candidateSaveBackService read both `httpMethod`/`fullPath` fallbacks), per-attribute PROVENANCE, prefer the specific interface, re-parent endpoints, drop emptied generic interfaces, consolidate request/response logical-data-entities.
- CONFLICTS HOLD for review (never auto-resolve): surfaced in the candidate review GRID — a per-candidate conflict badge/state, per-attribute side-by-side competing values with their source, a chooser, and a Finding recording the conflict; a conflict gates "clean approve". Plus WITHIN-SESSION bulk-resolve-by-pattern: after resolving one conflict, detect the N similar conflicts (same attribute + same competing sources) and offer "45 similar — resolve all the same way?". (Cross-scan preference memory is deferred, rides with future re-scan support.)
- HOOK POINT: a new reconciliation step in `discovery-service/src/services/discoveryV3Pipeline.ts` after the Stage-2 post-filter (where `dedupPackCandidates` runs, ~line 985), BEFORE LLM gap-fill — and folding in the LLM (Stage 3) + runtime-evidence (Stage 2.5) candidates by the SAME identity model — so the LLM and the persisted review list both see one clean set.
- Provenance/audit: record collapsed source-candidate ids + per-attribute source; emit a Finding per merge group so nothing is silently lost (oracle completeness).
