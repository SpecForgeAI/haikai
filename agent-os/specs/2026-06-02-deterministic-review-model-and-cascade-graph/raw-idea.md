Spec 1 — Deterministic review model + cascade/dependency graph + aggregation.

Part 3 of a sequenced 5-spec discovery-review-unification program (F → 0 → 1 → 2 → 3). Spec F (normalize findings review actions to Approve/Reject/Defer) and Spec 0 (universal identity-keyed cross-source candidate MERGE + conflict/provenance data model in candidate `data`) are BUILT + verified. Spec 1 is next.

**Problem.** After a discovery scan, a user faces huge lists of candidates + findings (code scan AND DB scan). Even after Spec 0 collapses duplicates, the user has no deterministic, precomputed view of *what's there* and *what depends on what*. There is no single backbone that answers "how many endpoints are pending review under this interface?", "if I reject this logical data entity, what cascades?", or "what's the blast radius of rejecting this service?". Both the existing candidate grid AND the future conversational "Architect" review persona (Spec 3) need to consume the SAME deterministic model — counts, groupings, dependency edges, and cascade blast-radius — rather than each recomputing ad hoc.

**This spec builds the deterministic backbone (NO LLM):**
1. A **deterministic review model** for a chosen scan selection — the unified set of candidates + findings across one code scan and/or one DB scan (max one of each, per the agreed unified-review framing), with their shared Approve/Reject/Defer review status (Spec F vocabulary, applied to BOTH candidates and findings), Spec 0 conflict flags (`data._conflicts`), provenance (`_addedBy`/`_mergedFrom`), and merge-group membership.
2. **Precomputed aggregation / counts** — by type, by review status, by source/tier, by conflict state, by merge group; rolled up so the grid header and the conversation agenda can both read them without re-deriving.
3. A **cascade / dependency graph** over candidates — parent→child structural edges (interface → endpoint → request/response logical data entity; service ownership; physical entity mappings) AND relationship-row edges (`interface_logical_entities`, `endpoint_data_effects`, logical↔physical mappings, data movements). For any candidate, compute the **blast radius**: the transitive set of dependents that a reject/defer would affect. This is the precomputed input that Spec 2's cascade-aware bulk accept/reject/save (preview→confirm) and Spec 3's conversation both consume.

**Hard constraints / locked cross-cutting decisions (from the program):**
- DETERMINISTIC code owns all counts / cascades / conflicts / actions. The LLM is only an enhancement layer introduced in Spec 3; Specs 0-2 must work fully without it.
- The model is the shared backbone for BOTH the grid (power-user / no-LLM fallback view) and the conversation (Spec 3). Same review-status vocabulary (Approve/Reject/Defer) for candidates AND findings everywhere.
- Respect the architecture meta-model (`gateway/src/config/prompts/shared/architecture-context-explainer.md`): logical↔physical are DISTINCT layers with EXPLICIT non-1:1 mappings (never assume 1:1); `classes`/`methods` are first-class entity types; polymorphic `*_points` wrappers are backend auto-managed and must NEVER be created/traversed as user candidates. The cascade graph must model these correctly (e.g. rejecting a logical entity touches its attributes, its logical↔physical mappings, and the endpoints referencing it via `endpoint_data_effects`).
- Spec 1 is the MODEL + GRAPH only. It does NOT execute bulk actions (that's Spec 2, incl. reject-suppresses-downstream-IR) and does NOT add the conversational persona (Spec 3). It must, however, expose the cascade blast-radius in the shape Spec 2's preview→confirm will render.
- Consumes Spec 0 outputs (merged candidates, `_conflicts`/provenance, merge groups) and Spec F's shared disposition vocabulary.

Open questions for the shaper to resolve with the user include: where the model + graph are computed and exposed (gateway vs AMS vs discovery-service; live-computed vs persisted/cached); the exact edge taxonomy and blast-radius semantics (does a reject cascade hard to children or just surface them for confirmation?); how scan selection feeds it; and how the grid begins consuming it in this spec vs. Spec 2/3.
