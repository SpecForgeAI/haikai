**Spec 2 — Cascade-aware bulk accept/reject/save + preview→confirm; reject suppresses the candidate's intermediate representation downstream.**

Part 4 of a sequenced 5-spec discovery-review-unification program (F → 0 → 1 → 2 → 3). BUILT + verified: Spec F (normalize findings review actions to Approve/Reject/Defer), Spec 0 (universal identity-keyed cross-source candidate MERGE + conflict/provenance data model in candidate `data`), Spec 1 (DETERMINISTIC review-model + typed cascade/dependency graph + surface-only blast-radius + aggregations backbone, computed live on read in discovery-service, exposed via a read endpoint, proxied by the gateway, with the candidate grid's count memos re-pointed onto it). Spec 2 is next.

**Problem.** After Spec 1, the user can SEE the review model — counts, the typed dependency graph, and, per candidate, the surface-only blast-radius (the transitive set of dependents a reject/defer WOULD affect, each tagged with the edge that pulled it in). But Spec 1 deliberately never MUTATES anything: it computes, it does not act. There is no cascade-aware way to accept/reject/defer/save many candidates at once with a clear preview of consequences, and — critically — a "rejected" candidate today is at best hidden in the grid; its rich intermediate representation (IR) still flows downstream into target-state building and the backlog/spec (book-of-work) generation. For a like-for-like migration oracle, "rejected" must mean EXCLUDED EVERYWHERE, not merely hidden.

**This spec builds the deterministic bulk-action + suppression layer (NO LLM):**
1. **Cascade-aware bulk actions** over a selected SET of candidates (and their linked findings): bulk **Approve / Reject / Defer** (shared Spec F vocabulary for candidates AND findings) and bulk **Save** (commit the approved set into the architecture model via the existing save-back path). The action is "cascade-aware" because it consumes Spec 1's blast-radius: acting on a parent surfaces its dependents.
2. **Preview → confirm.** Before any mutation, show a DETERMINISTIC preview built from Spec 1's blast-radius + aggregations: exactly which candidates/findings the action will touch, which are pulled in by cascade and via which edge (provenance), and the net counts. The user confirms (or adjusts the set), THEN the batch applies. No silent cascades.
3. **Reject suppresses the IR downstream (the oracle-completeness requirement).** A rejected candidate's intermediate representation must be EXCLUDED from every downstream consumer — target-state architecture building AND backlog/spec (book-of-work) generation — not just hidden in the review grid. "Rejected" = excluded everywhere. This must be REAL wiring into the downstream consumers, not a flag that is set but ignored (the user treats such stubs as defects).

**Hard constraints / locked cross-cutting decisions (from the program):**
- DETERMINISTIC code owns all counts / cascades / conflicts / actions. Specs 0-2 must work FULLY without the LLM; Spec 3 only adds a conversational persona on top of these exact bulk mechanisms.
- Spec 2 AUGMENTS the existing candidate grid (the power-user / no-LLM view): same shared decision store, the SAME approve/reject/save mechanisms the future conversation will call. The preview→confirm surface renders Spec 1's already-computed blast-radius.
- Findings & candidates share Approve/Reject/Defer everywhere. A finding linked to a rejected candidate is part of the cascade story.
- Respect the architecture meta-model (`gateway/src/config/prompts/shared/architecture-context-explainer.md`): logical↔physical distinct + EXPLICIT non-1:1; classes/methods first-class; `*_points` polymorphic wrappers backend-managed (never user-acted). The cascade application + IR suppression must honor this.
- Review-status transitions are any→any (Spec F) with a `previous_review_status` audit; bulk actions should preserve that audit. AMS speaks snake_case at the wire by default.
- Spec 1's backbone is READ-ONLY and never persisted; Spec 2 is where the WRITES happen (review-status mutations + the save-back commit + the IR-suppression marking), through the existing write paths where they exist.

**Open questions for the shaper to resolve with the user include:** the cascade APPLICATION semantics (does rejecting a parent HARD-cascade the reject to all dependents, or does the preview let the user curate which dependents are included? — Spec 1 left this hard-cascade decision explicitly to Spec 2); WHERE and HOW IR suppression is enforced (the exact downstream consumption points for target-state building + book-of-work generation, and whether suppression is a read-time filter keyed on rejected candidates vs a marking on the IR vs exclusion at save-back) — this requires tracing the real downstream IR flow; atomicity of a bulk apply (all-or-nothing transaction vs best-effort batch + partial-failure reporting); what bulk **Save** commits and via which path (`mcp-server` `candidateSaveBackService` / AMS bulk endpoints); reversibility/undo of a bulk action (any→any transitions exist, so a bulk reject can be re-approved — confirm the round-trip incl. un-suppressing the IR); and how much of the preview→confirm UI lands here vs is reused by Spec 3's conversation.
