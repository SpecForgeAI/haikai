# Chat sessions and audit

How [[chat-executors]] persist conversations across requests, identify them, and audit them. Three small modules in `src/chat/`: `session_store.py`, `audit_logger.py`, `persistent_store.py`.

## Two distinct UUIDs

The chat layer carries two UUID concepts that are easy to confuse:

| UUID | Generated by | Lifetime | Stored in |
|---|---|---|---|
| **Deterministic project UUID** | `uuid5(NAMESPACE_DNS, f"{company}_{project}")` (in each executor) | Forever — same company/project always derives the same UUID | Used in-process; never written |
| **Active session UUID** | `uuid4()` (random) in `session_store.create_active_session` | Until cleared or replaced | `<workspace>/<company>/<project>/.claude/active_session.json` |

The deterministic UUID is the project's *identity*; the active session UUID is one *instance* of a chat conversation. Each `POST /shape-spec/stream` either creates a new active session or resumes the existing one. The executor's `session_uuid` is overwritten with the active session value before `stream_message` runs.

## `session_store.py`

Thin module — 3 functions:

```python
create_active_session(workspace_dir, company, project) -> str  # new uuid4
get_active_session(workspace_dir, company, project) -> str | None
clear_active_session(workspace_dir, company, project) -> bool
```

Path: `<workspace>/<safe(company)>/<safe(project)>/.claude/active_session.json`. The `safe(...)` segment validation is critical — see security note below.

## Path-traversal fix (commit `014de40`)

Earlier versions interpolated `company` and `project` URL segments straight into the workspace path. A request with `company=".."` would resolve `<workspace>/../<project>/.claude/active_session.json`, escaping the workspace.

Fixed by routing both segments through `safe_segment(...)` (in `src/path_safety.py`), which rejects:
- `..` and any path that contains it
- `/` or `\` in the segment
- Empty strings or pure-whitespace
- Windows drive letters

The same defense pattern is used in `tool_executor._safe_workspace_path` ([[tool-executor]]) and the API layer's `_safe_project_dir` ([[api-layer]]). Single source of truth at `src/path_safety.py`.

## `audit_logger.py`

Logs every user/assistant message to `chat_logs/messages.jsonl` (one JSON object per line) in the project's chat-logs directory.

```
{"role": "user", "message": "...", "timestamp": "...", "session_id": "..."}
{"role": "assistant", "events": [...], "timestamp": "...", "session_id": "..."}
```

Append-only. Never rewrites prior lines. Crash-safe: a partial line at EOF is recoverable (just drop the trailing partial record on re-read).

The chat-logs directory is `<workspace>/<company>/<project>/chat_logs/` — same project root the path-safety helpers protect.

## `persistent_store.py`

Per-project key/value persistence layered on top of audit logs. Used for state that needs to survive across sessions but isn't tied to a single message — e.g. memory-middleware deltas, last-known spec folder, last-completed phase.

Distinct from the [[job-queue]]'s SQLite layer (which stores `Job` records, not chat-derived state).

## How sessions resume across machine boundaries

Active session resumption normally just requires the JSON file to be present. But Claude CLI session storage at `~/.claude/projects/<encoded-path>/<uuid>.jsonl` is on a different path and may not exist when a fresh container or a different developer's machine takes over.

Two-layer backup:
1. **Active session file** — `<workspace>/.claude/active_session.json` (in the project workspace, committable to git).
2. **Session jsonl backup** — `<workspace>/haikai/specs/<spec>/<uuid>.jsonl`. `ClaudeChatExecutor.persist_session_to_spec` copies the live session here after each call; `restore_session_from_spec` copies it back to `~/.claude/projects/...` when missing on the new host.

This is what makes [[haikai-sdd]] specs portable — commit the spec folder including the `.jsonl`, and any clone can resume the conversation.
